Installing add-ons

Every Windows installer runs inside the simulator's prefix, and a handful of things go wrong the same way for many of them. This page has the order of work and those shared traps. The page of each add-on says what is special about it.

The order of work

  1. Have Proton FS2024 selected in Steam

    Most of the hard add-ons need it, and the simulator has to have started once with it. Start here builds it and says how to pick it.

  2. Close the simulator and every program of its prefix

    That includes the stores, and anything the previous installer left open in the tray. bin/flightsim-on-linux machine --json lists what still holds the prefix in prefix_in_use and prefix_programs. Install one add-on at a time.

  3. Get the installer from the vendor

    Each add-on page says where it comes from. addon install without a file prints the same, as the next section shows.

  4. Run the installer

    ~/flightsim-on-linux/bin/flightsim-on-linux addon install <id> /path/to/the-installer

  5. Fix it and check it

    ~/flightsim-on-linux/bin/flightsim-on-linux addon apply <id>
~/flightsim-on-linux/bin/flightsim-on-linux addon check <id>

    addon apply runs the fix and then the check, so the second command is for later, after an update.

  6. Add the menu entry and the watcher, if the add-on has them

    See Shortcuts and watchers. Programs that talk to the simulator are started after the simulator, from the menu or by a watcher. The ground rules say why.

What addon install does

Without a file it only prints where the program comes from, whether it is paid or free when that is known, and what kind of installer it is:

~/flightsim-on-linux/bin/flightsim-on-linux addon install msfs-autofps

The kind is one of four. installer is a Windows installer you download. store is a store app that downloads the installer for you. native is a Linux program. manual is a set of steps nobody has scripted. When the add-on has an install script and needs a file, the command ends with the line to run next.

The helper app does the same in dialogs: Install an add-on shows where to get it, asks for the file you downloaded and runs the command.

With a file, it runs the add-on's own install script on that file:

~/flightsim-on-linux/bin/flightsim-on-linux addon install msfs-autofps ~/Downloads/MSFS_AutoFPS-installer-v0.5.5.0.exe
  • It refuses while the simulator runs, or while any program is open in the prefix, and names those programs: close the simulator and every program of its prefix first; installers run alone. Nothing is started. An add-on with a prefix of its own, such as FlightSim Dispatch, skips this.
  • It runs the installer in the simulator's prefix with the Proton the simulator last ran with. It does not use your system Wine.
  • It starts the installer without NoDefaultCurrentDirectoryInExePath in the environment. Claude Code sets that variable in its shell, and Wine installers fail with it. If an AI agent drives your terminal and you start a Wine command by hand, put env -u NoDefaultCurrentDirectoryInExePath in front of it.
  • Most install scripts then wait up to a minute for the prefix to go quiet. If programs are still open, they say programs are still open in the prefix after the installer; close them before the next one. Close them before you install the next add-on.
  • If the installer exits with a code other than 0, the command says so and stops. If it exits with 0, it prints addon apply for that add-on as the next step.

A native add-on with an install script needs no file and runs at once. An add-on without an install script gets its source printed, and you run the installer yourself, as the ground rules describe. An add-on with nothing to install says so.

Installers run alone

This is the rule behind most failed installs. Each protontricks-launch starts its own container, and the Wine server of a prefix belongs to whoever started first. A program that runs in a different container from the server can't list the modules of any process, its own included, and Windows calls that fail with error 5 ("Access denied"). .NET installers do that at the very end, to register themselves, so the failure arrives after the files are already unpacked.

Measured on the test machine on 13 October 2026: the ChasePlane installer ended with "Installation failed" and an access denied message while PMDG Operations Center 3 was open in the same prefix. With nothing else open, ChasePlane and Flow installed on the first try. Calling the system's wine on the prefix with Operations Center 3 open failed the same way. Why the kernel refuses is a guess, based on ptrace_scope. What was measured is the table of outcomes.

So: one installer at a time, with the simulator and every other program of the prefix closed. The ground rules have the rest, and the command to run an installer by hand:

protontricks-launch --no-term --appid 2537590 /path/to/Setup.exe

Store apps leave the installer unrun

Contrail and simMarket download the installer .exe of a product into the prefix's Downloads folder and stop. Nothing runs it. That folder is drive_c/users/steamuser/Downloads under the prefix that bin/flightsim-on-linux machine --json prints as prefix. Close the store, then give the file to addon install or to protontricks-launch. The store holds the prefix while it is open, and an installer started next to it fails as above.

Paths over 260 characters

Windows installers stop at 260 characters in a path, and Wine does not lift the limit. On 18 October 2026, on the test machine, the .NET 4.8 installer exited with code 42 when the path to it, as Wine sees it with a Z: drive in front, passed about 260 characters. A Fenix helper printed Cabinet extraction failed: 122 from a work folder of about 290 characters. Both worked from the cache in ~/.cache/flightsim-on-linux and from short folders.

Keep installers in a short folder such as ~/Downloads, not deep inside a project tree. Don't point FSOL_CACHE at a long path: the Fenix add-on refuses a cache folder longer than 150 characters, before it downloads anything, and asks for a shorter one.

.NET Framework 4.8 in a Windows 11 prefix

The prefix of Proton FS2024 reports Windows 11 (build 22000). On 18 October 2026 the .NET 4.8 installer, run as ndp48-x86-x64-allos-enu.exe /q /norestart in a new prefix, exited with code 0 and installed nothing. Its own log said that .NET 4.8 or later was already installed. The exit code reports success while nothing was installed.

The .NET Framework 4.8 add-on handles it: addon apply dotnet48 saves the Windows version keys (Windows NT\CurrentVersion in both registry views, and Version under HKCU\Software\Wine), switches the prefix to Windows 7 with winecfg -v win7, installs, and puts the keys back one value at a time. It stops if the result doesn't match what it saved. winecfg -v win10 is not a way back: it writes another build and another UBR and rewrites the 32-bit view. The .NET 4.8 page describes what the command does, and addon apply fenix-a320 runs it as its first step. If another add-on asks you to install .NET 4.8 yourself, expect the same exit 0, and take that script as the only procedure that was tested.

Wine's PowerShell exits with zero

The powershell.exe in a prefix is a stand-in from Wine. It accepts any command line, prints nothing and exits with 0. A program that uses PowerShell as a tool gets an empty answer that looks like success.

On the test machine this broke the PMDG Operations Center 3 twice. Its updater checks the installer's signature by reading JSON from PowerShell, and ended with "Unexpected end of JSON input". Its installer asks PowerShell whether a process is running in the install folder, gets a 0, reads it as "yes", and says it can't close the PMDG OC3 when nothing runs. Running the installer with WINEDLLOVERRIDES=powershell.exe=d makes Wine stop offering the stand-in, so the installer falls back to tasklist | find, which Wine implements.

Use that setting for installers built with electron-builder. The install scripts of PMDG Operations Center 3, Orbx Central and Volanta set it. This project ships no PowerShell that always answers "valid": it would switch off a real security check for good.

A mod that is only a Windows PowerShell script and only rewrites files in one Community package can run from the native pwsh instead, without the prefix. Three things differ from Windows: backslashes in its paths have to become forward slashes, anything it compiles against the .NET Framework's System.Web.Extensions needs a stand-in, because modern .NET doesn't have it, and the Community folder has to be passed in directly, because %LOCALAPPDATA% doesn't exist.

WebView2

Several installers and managers draw their pages with WebView2, a Chromium that comes as a runtime. Two things can go wrong, and they are separate.

The first is a page that stays grey, white or empty. That is the Wayland driver losing what the Chromium process drew. It needs Proton FS2024 and the WebView2 policy in the prefix, set once. The Proton FS2024 page has the command and the rules: a value named after a program replaces the * value instead of adding to it, and GSX ignores the policy and takes WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS.

The second is the runtime itself. This project doesn't install it. The prefix of the test machine holds version 146.0.3856.62, registered on 22 July 2026, and nothing records how it got there. No installer failure is recorded as caused by a missing runtime, so there is no tested way to install it here.

Packages that are links

An add-on organiser can move a package out of Community and leave a Linux symlink in its place. Wine shows that symlink to Windows programs as an ordinary folder. Two things follow, both on the test machine:

  • On 17 October 2026 a Fenix Installer update replaced two aircraft packages that were symlinks. The folders they pointed at vanished from the organiser's library, with nothing in the trash, and the links in Community pointed to nothing. In a throwaway prefix with the Proton of that day, rd /s /q on the link, and a move followed by rd, each deleted the whole target folder and left the link dangling. Which call the Fenix Installer makes was not measured.
  • On 16 October 2026 the MSFS AutoFPS 0.5.4.4 installer stopped halfway, at "Deleting old Widget Version", on a link made by an organiser. The install script of MSFS AutoFPS removes that one link before it runs the installer, and prints where it pointed.

Before you run an installer or an update, list the links in your Community folder with find . -maxdepth 1 -type l, run from inside it. For each package the installer will replace, remove the link itself with rm, without a trailing slash, so that only the link goes and your organiser's copy stays where it is. The installer then creates a real folder. Junctions that Windows installers made themselves, such as GSX's, are a different case, and the ground rules cover them.
