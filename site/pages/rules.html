title: Ground rules description: Rules that apply to every Windows add-on in the MSFS 2024 Proton prefix: installers, running next to the simulator, your screen setup, freezes and ntsync, Community links, fonts and WPF. ---

Ground rules

These apply to every add-on. Each one took hours to find on the test machine, because from the outside it looks like a bug in the add-on.

Run installers alone

Close the simulator and every other program of its prefix before you run an installer or an updater, and run one at a time. Store apps count: Contrail, simMarket, Orbx Central, the FSDT installer. With another program open, .NET installers fail with "Access denied" while reading their own modules, usually at the very end ("Registering installed application").

Contrail and simMarket download an installer .exe into the prefix's Downloads folder and stop there. Close the store, then run that installer yourself.

To install into the prefix from a terminal:

protontricks-launch --no-term --appid 2537590 /path/to/Setup.exe

Programs that run next to the simulator join its container

Steam starts the simulator inside the Steam Linux Runtime container. A Windows program started some other way while the simulator runs ends up in a different container and gets the same "Access denied" as above. Programs that talk to the simulator (AutoFPS, SayIntentions, Active Sky, vRAAS, Lorby AAO) have to be started inside the simulator's own container. The add-on guides give a launcher for each.

To start any other Windows program there, give its Windows path to bin/flightsim-on-linux run. It enters the simulator's container and runs the program with the simulator's environment and Proton. Settings for that one program go before the path:

bin/flightsim-on-linux run WINEDLLOVERRIDES=d3d9=d 'C:\Program Files\App\App.exe'

The simulator has to be running already.

A program left open in that container keeps Steam showing the simulator as running after you quit it. Close your add-ons before you quit the simulator.

Your screen setup changes what works

This section is about your machine, not about any one add-on: the Wine display driver, HDR, your monitors and, if you have two GPUs, which one composes the desktop. The test machine has an RTX 4080 with 16 GB of video memory, the Radeon built into its Ryzen, and an HDR TV with a second monitor beside it, so some of what follows won't apply to yours. The add-on fixes in this repository don't depend on any of it.

Wine draws windows through one of two display drivers. Proton uses the X11 driver, which runs through XWayland in a Wayland session, unless the launch options hold PROTON_ENABLE_WAYLAND=1; then it uses the Wayland driver. The test machine runs the Wayland driver, and there the tray icons of GSX, ChasePlane and Volanta show up in a small window of Wine's own explorer.exe instead of the KDE tray. In Proton-CachyOS (Wine 11.0) the X11 driver speaks the X11 tray protocol, and the Wayland driver speaks no tray protocol at all, not even the one KDE uses on Wayland. Plasma already runs a proxy that carries X11 tray icons into its tray, so nothing is missing on the KDE side. Nobody has tested whether the icons really reach the KDE tray under the X11 driver.

The driver also decides HDR. The test machine starts the simulator with PROTON_ENABLE_WAYLAND=1 PROTON_ENABLE_HDR=1. KWin doesn't manage colour for XWayland windows, so under the X11 driver the desktop gives the simulator no HDR. gamescope can add it, but gamescope shows one window at a time: the FSLabs Control Center, which the simulator opens itself, covered the simulator and left it without a mouse pointer.

How many monitors you have, and which way they face, matters as well. gamescope offered HDR on the TV but not on the portrait monitor, depending on which screen its window sat on. The simulator reads the screen once, when it starts, and after a start on the wrong monitor its HDR10 option stayed locked. Start the simulator on the screen you play on.

On a machine with two GPUs, the one that composes the desktop costs frames. With KWin on the integrated Radeon and the simulator in 4K, every frame went from the RTX 4080 to the Radeon to be composed and back to the RTX to be shown. The Radeon sat at 100% and the simulator ran at 51 FPS. With KWin on the RTX, the same scene ran at 62 FPS and the Radeon stayed idle. You pay for that in video memory: with the simulator closed, the desktop took 1554 MiB of the RTX instead of 177 MiB. Sending desktop programs to the GPU the compositor doesn't use is worse. Their windows came out black, and under Wine's Wayland driver such programs die with importing the supplied dmabufs failed, the same message as in the WPF section below.

You can choose which GPU composes the desktop. If you don't, KWin uses the card the kernel marks as the boot display, the one the firmware drew the boot screen on. On the test machine that was the RTX at one boot and the Radeon at the next, and the simulator got slower with nothing else changed. A file in ~/.config/plasma-workspace/env/ that exports KWIN_DRM_DEVICES with the card you want listed first fixes it from your next login. Name the cards by PCI address, from /dev/dri/by-path/, because the cardN number can change. qdbus6 org.kde.KWin /KWin supportInformation | grep 'OpenGL renderer' shows which GPU KWin is using.

bin/flightsim-on-linux doctor lists the Wayland sockets of your session, the Wine display driver the simulator loaded (or will load, going by your launch options) and how many monitors are on. A script that starts a program next to the simulator must not write WAYLAND_DISPLAY, DISPLAY or XAUTHORITY into itself: a ChasePlane watcher once had wayland-0 written in, in a session whose socket was wayland-1. bin/flightsim-on-linux run copies all three from the simulator's process.

If the simulator freezes, turn ntsync off first

Proton can use ntsync, a Linux kernel driver for Windows-style synchronization, and it does whenever the kernel has /dev/ntsync. With plain Proton-CachyOS in July 2026, the test machine froze in the main menu or while loading an aircraft, and turning ntsync off fixed it. Not every freeze is ntsync: on 14 October 2026 the simulator froze twice right after the Fenix runner started and quit, once with ntsync already off. On 17 October 2026 it flew with ntsync on and didn't freeze. The add-ons on this site were tested with ntsync both on and off.

So ntsync can stay on. If the simulator freezes in the menu or during an aircraft load, turn it off first: in Steam, right-click Microsoft Flight Simulator 2024, choose Properties, and put this at the start of Launch Options:

PROTON_NO_NTSYNC=1 %command%

If you already have launch options, add PROTON_NO_NTSYNC=1 before %command%. PROTON_USE_NTSYNC=0 looks like it should do the same, but Proton ignores it. bin/flightsim-on-linux doctor says whether ntsync is on. With the simulator running, it counts the /dev/ntsync handles its wineserver holds, so it reports what the simulator really uses, not just what the launch options say.

Don't kill the simulator while it loads

On the test machine, a simulator force-quit during its loading screen came back with every Community package switched off. It gave no warning; the aircraft were gone from the list. It had marked each Community package SystemDisabled in Content.xml, in your profile folder inside the simulator's base folder. Force-quits after the main menu didn't do this.

With the simulator closed, this turns back on only the Community packages the simulator switched off, and leaves the ones you switched off yourself (UserDisabled) alone:

find ~/.local/share/Steam/steamapps/compatdata/2537590/pfx/drive_c/users/steamuser/AppData/Roaming/"Microsoft Flight Simulator 2024" -maxdepth 2 -name Content.xml -exec sed -i -E 's/(<Package name="community[^"]*" active=")SystemDisabled(")/\1Activated\2/' {} +

If your simulator is in another Steam library, use that library's steamapps/compatdata/2537590; bin/flightsim-on-linux machine prints it. bin/flightsim-on-linux doctor warns when the simulator has switched Community packages off, and prints this command with your own path.

Junctions in Community look broken from Linux

GSX, SayIntentions and the FSDT sceneries put Windows junctions in Community. From Linux they look like empty folders with a ? at the end of the name. That is normal: inside Wine they point to the right place.

Don't move or rename them from Linux, and don't let an add-on organiser replace them with symlinks. A junction moved from Linux loses its target and the add-on disappears from the simulator. To repair one, delete the link and the empty folder, then let the add-on recreate it: Relink in the FSDT installer for GSX, or the add-on's own installer.

The same goes the other way: a Windows installer can't update a package that an organiser turned into a Linux symlink. Wine can't delete a Linux symlink through Windows calls, and the installer stops halfway. Remove the link first.

WPF programs draw in software

Several add-on apps are WPF programs (Lorby AAO, AutoFPS, vRAAS, the FSLabs Control Center, the Fenix runner). On the test machine, under Wine's Wayland driver, they crashed the moment their window should appear, with importing the supplied dmabufs failed in the log. Started with Direct3D 9 turned off, or with this one setting in the prefix, they draw in software, as WPF does on a Windows PC without graphics acceleration:

protontricks -c 'wine reg add "HKCU\Software\Microsoft\Avalon.Graphics" /v DisableHWAcceleration /t REG_DWORD /d 1 /f' 2537590

It applies to every WPF program in the prefix. To undo it, run the same command with reg delete "HKCU\Software\Microsoft\Avalon.Graphics" /v DisableHWAcceleration /f. doctor tells you whether the setting is there. When it's missing and your launch options turn on the Wayland driver, it warns.

Missing Windows fonts

A prefix has no Segoe UI or Consolas, so text in add-on windows falls back to a thin, jagged Times New Roman. Map them to free fonts under HKCU\Software\Wine\Fonts\Replacements. Wine ignores a replacement whose font isn't installed, so the name has to match an installed font family exactly. These names work on the test machine: Noto Sans for Segoe UI and Segoe UI Bold, Noto Sans Medium for Segoe UI Semibold (Arch's noto-fonts package has no SemiBold), DejaVu Sans Mono for Consolas, DejaVu Sans for Verdana and Noto Serif for Palatino Linotype. winecfg has no option for this. doctor checks all six and prints one command that adds the missing ones.

Calibri is the exception: Wine's GDI+ only finds a font whose full name matches its family name, so Active Sky needs a real file named Calibri, built from Carlito. Its guide has the script.

The first load of a heavy aircraft is slow

The first time you load an aircraft with a large WASM module, such as the MD-11, the simulator compiles it for several minutes. It is cached afterwards. Don't kill the simulator thinking it froze, for the reason above.

Never share these

Some add-ons write licence keys into plain-text logs. The FSLabs CCLog.txt is one. Don't paste such files into an issue, a forum post or an AI chat. When a guide asks for a log, it says which one and what to remove first.
