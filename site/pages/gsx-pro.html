title: FSDT GSX Pro description: How to install and run FSDT GSX Pro in MSFS 2024 under Proton: the FSDT universal installer you run once yourself, the copy of wine-mono the updater needs, what that copy changes, and how to undo every step. ---

FSDT GSX Pro

Tested with GSX Pro 4.0.23 on 17 October 2026. It is the hardest add-on in this guide to get right: the FSDT updater needs a copy of wine-mono in your prefix with two methods changed, an exe.xml entry has to be rewritten, and one step sits next to your licence. Read the next section before you run anything.

Read this first

touches add-on files The fix changes a copy of wine-mono that lives in your prefix, the GSX entry in exe.xml, and files in system32. It doesn't edit a program file of GSX or of the FSDT Addon Manager.

The FSDT universal installer spends an activation, and this tool never runs it. FSDT_Universal_Installer.exe resets the local state of the installation and forces a new activation, so every run uses up one of the activations your licence has. On the test machine it ran once, in July. Run it once yourself, as "Install it" says, and never again on a prefix where GSX is already activated. Nothing here runs it for you: there is no install script for GSX Pro on purpose, and addon install gsx-pro only prints where to get the program. The commands on this page don't read, print or change serial numbers or activation state. The registration they write is generated from the manifest of QlmLicenseLib.dll, a file that holds no serial.

What the two changed methods do. The FSDT updater, Couatl_Updater2.exe, is a .NET program and runs on wine-mono. Every time it opens it calls RegistrationServices.RegisterAssembly on the licence library, and in wine-mono that method only throws NotImplementedException. The updater catches the exception, marks the installation as incomplete, and the Install button does nothing. The fix makes RegisterAssembly return true without doing anything. That is honest only because apply writes the COM registration the method would have made, from the manifest. The second method is Process.Responding. GSX starts its engine through a watchdog, couatl64_boot.exe, that asks every few seconds whether the engine answers, and in wine-mono the property is always false. On 13 October 2026 the watchdog killed a working engine 60 seconds after each "stopped responding", seven times in a row, once every 80 seconds. The fix makes the property return true. The price is that the watchdog can no longer restart an engine that is really hung: use the restart command in the GSX panel.

How to undo it. addon undo gsx-pro puts back everything the fix changed, from the originals it kept in compatdata/2537590/flightsim-on-linux-backup/gsx-pro. "Undo" below lists each step. By hand, deleting drive_c/windows/mono in the prefix removes the wine-mono copy, and the two patches go with it.

Get it

GSX Pro is made by FSDT (www.fsdreamteam.com) and is paid, with a limited number of activations. The program you download is FSDT_Universal_Installer.exe, version 1.3.6 on the test machine, an Inno Setup installer. It installs the Addon Manager, and the products come through its updater, Couatl_Updater2.exe. The version on the test machine was GSX Pro 4.0.23.

Install it

Close the simulator and every other program in its prefix, and run one thing at a time. The ground rules explain why and show how to run an installer by hand. Then:

  1. Run the universal installer once, with the simulator closed. This is the step that spends an activation, and the only time it runs. Which command ran it on the test machine wasn't recorded; protontricks-launch --no-term --appid 2537590 /path/to/FSDT_Universal_Installer.exe is the way the rules give for any installer.
  2. Make the fixes the updater needs: 
    ~/flightsim-on-linux/bin/flightsim-on-linux addon apply gsx-pro
    It stops with a message if the Addon Manager folder has no QlmLicenseLib.dll.manifest, which means step 1 didn't happen.
  3. Open the updater: 
    ~/flightsim-on-linux/bin/flightsim-on-linux addon launch gsx-pro
    It runs Couatl_Updater2.exe /SILENT /INSTALLMODE, which shows the list of products with their Install and Activate buttons. Click Install on GSX Pro. The command refuses while the simulator or any program of the prefix is open. An update works the same way.
  4. When the install has finished, run addon apply gsx-pro once more. The updater adds the GSX entry to exe.xml itself, and the fix can only change an entry that exists.

Without the fixes, three things go wrong in this order, measured on the test machine in July and on 13 October 2026. The Install button does nothing, and the updater's last log line, in the registry value updater_lastlogline under HKCU\Software\Fsdreamteam, reads Cannot install GSX Pro: Addon Manager install is incomplete (QlmLicenseLib.dll not registered). With that solved, the FSDT installer still prints that it cannot run C:\windows\Microsoft.NET\Framework\v4.0.30319\RegAsm.exe, because the folder has no such program. And with that solved, the 13 GB of GSX Pro and the 5 GB of World of Jetways download from FSDT's server, but the engine doesn't arrive. The engine, the sounds and part of the textures live in packages on GitHub, and the updater downloads those with curl.exe, which Wine doesn't have. The updater then falls back to a method that asks for a URL that answers 404, and the install looks finished while couatl64_boot.exe is missing, and exe.xml already points at it.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply gsx-pro

It prints the first two warnings above, then does these things, and runs the check at the end:

  • RegAsm.exe. It links RegAsm.exe in Microsoft.NET/Framework/v4.0.30319 and Framework64/v4.0.30319 to the stub Wine ships, so the updater's call to start it succeeds. The stub does nothing; the COM registration comes from the next step. A RegAsm.exe that is already there is left alone.
  • COM registration. It generates a .reg file from the QlmLicenseLib.dll.manifest in the Addon Manager folder (22 classes in the version on the test machine) and imports it with regedit, in the four places the updater might read: both views of HKEY_CLASSES_ROOT and both of HKCU\Software\Classes. The updater is a 32-bit program, which is why the 32-bit views matter. It keeps the matching removal file in the backup folder only when this run did the registration: a registration that was already in the registry is left to whoever made it, and undo does not remove it.
  • The wine-mono copy. It copies the newest wine-mono folder of Proton to drive_c/windows/mono/mono-2.0. Wine looks there before it looks in Proton's folder, so Proton's own files stay as they are and the copy survives Proton updates. In the copy it changes RegisterAssembly in mscorlib.dll to return true and Process.Responding in System.dll to return true, and it keeps the original of each. It finds the two methods by name in the .NET metadata, checks that their bodies are what it expects (newobj then throw, and ldc.i4.0 then ret), and refuses to touch a file where they are not. The copy affects every .NET Framework program in the prefix that runs on wine-mono, not only the updater, and it stays at the wine-mono version it was copied from. When Proton ships another version, check says so, and apply copies again.
  • curl.exe. It downloads curl 8.22.0 (build 3) for Windows from curl.se, checks the zip against a sha256 pinned in the script (f38b0ac2e3a280fd414b607c874a21e6dd4d1ed0e2ae622afbf0020917446561), and copies curl.exe and its CA bundle into system32 and syswow64. The updater is 32-bit and looks in system32, which for it is syswow64; the 64-bit program runs from both. The download stays in the cache folder. To use another build, set GSX_CURL_URL and GSX_CURL_SHA256 before apply. A file that already exists is kept in the backup folder first.
  • The engine entry in exe.xml. GSX ignores the WebView2 policy that other add-ons use. Its flightsim.to window takes the browser options from the environment variable WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS instead. apply builds com-environment.exe, a small program that sets that variable to the four software-drawing options (--in-process-gpu --disable-gpu --disable-gpu-compositing --disable-software-rasterizer), starts the engine's couatl64_boot.exe in its own folder and waits for it. It needs x86_64-w64-mingw32-gcc to build (mingw-w64-gcc on Arch, gcc-mingw-w64-x86-64 on Debian and Ubuntu). It copies the program to C:\flightsim-on-linux and points the Couatl entry of exe.xml at it, with the original path as its argument. The original exe.xml is kept in the backup folder. If the entry already starts through com-environment.exe, apply only puts the program back when it is missing, and says it did not change exe.xml. If the entry starts through it with other WebView2 options than these four, apply changes nothing, fails, and says to put the entry back to starting couatl64_boot.exe directly before it runs again; it never rewrites an entry it did not make. On 17 October 2026 the browser of the GSX window came up with the options, and the flightsim.to page appeared inside the window.

GSX also needs Proton FS2024. Its flightsim.to window is a WebView2 whose content comes from a second process, and stock Wine drops what that process draws, so the window stays white. The patch is win32u-cross-process-child-windows.patch.

Start it

The GSX engine starts from exe.xml, so there is no service to switch on. The updater has a menu entry:

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut gsx-pro

This writes an entry called "FSDT Installer" in your application menu, with the updater's own icon when 7z and magick are installed. It does what addon launch gsx-pro does. Despite its name, that entry is the updater. Don't run FSDT_Universal_Installer.exe again: that spends an activation. Shortcuts and watchers has the details.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check gsx-pro

It prints up to nine lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • RegAsm.exe exists in both v4.0.30319 folders;
  • every class of the manifest is in the registry with mscoree.dll as its server;
  • the wine-mono copy has the patched RegisterAssembly, and the patched Process.Responding;
  • the copy is the wine-mono version Proton ships now. A copy of an older version that still has both patches passes too, and the line names both versions and says to run addon apply gsx-pro to refresh it, then addon apply axis-and-ohs. An older copy without the patches fails;
  • curl.exe and its certificates are in system32 and syswow64;
  • Proton was built with win32u-cross-process-child-windows.patch;
  • exe.xml starts the engine through com-environment.exe with the four options, and that program exists.

The exe.xml lines fail until GSX is installed. After a Proton update the wine-mono line is the one to watch: it stays ok while the old copy has both patches, and when you are ready, run apply to take the new copy and run addon apply axis-and-ohs too if you use it, because it shares the copy and the new copy starts without its patch.

Known problems

  • A really hung engine is no longer restarted by the watchdog. Use the restart command in the GSX panel.
  • A GSX update that rewrites exe.xml brings the white window back. Run addon apply gsx-pro again.
  • Every .NET Framework program of the prefix that runs on wine-mono uses the copy. If one starts failing after a Proton update, run addon check gsx-pro, then addon apply gsx-pro to copy again. Deleting drive_c/windows/mono and running apply does the same by hand.

These look like errors and aren't:

  • In Community, the GSX packages show on Linux as empty folders with a ? at the end of the name. That is how this Wine stores a junction: an empty folder with the target in the extended attribute user.WINEREPARSE. Inside Wine the name has no ? and the folder lists its files. Don't replace them with Linux links, and don't move them from Linux: a move keeps the name and loses the attribute.
  • A WINE_MONO_TRACE of the updater shows thousands of certificate exceptions, COMException and IndexOutOfRangeException. They are inside the updater and stop nothing.
  • The WMI error 0x8004100e is the updater looking for Windows Defender.
  • exception UNRECOGNIZED_ID (3) in call SetDataOnSimObject in Couatl.err, about half a minute after the engine starts. It keeps appearing while the engine stays up.

On 13 October 2026, with the watchdog fixed, the engine stayed up for more than 14 minutes and served a request. That run was in the simulator.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo gsx-pro

Close the simulator and the updater first. It puts the GSX entry in exe.xml back to starting couatl64_boot.exe directly and removes com-environment.exe; removes the QlmLicenseLib registration with the removal file it kept; gives back the two original methods; deletes the wine-mono copy when this tool made it and no other add-on uses it (Axis and Ohs uses it too); takes curl.exe and the certificates out of system32 and syswow64, or puts back the ones that were there; and removes the RegAsm.exe links it made. It leaves the FSDT programs alone, with their licences and serial numbers, and every file the FSDT installers wrote. After an undo the updater goes back to refusing to install, and a running GSX engine goes back to the watchdog killing it.
