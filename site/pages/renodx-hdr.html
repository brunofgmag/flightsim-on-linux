RenoDX HDR for MSFS 2024

Tested with version 1 of the RenoDX HDR mod for Microsoft Flight Simulator 2024, from Nexus Mods (mod 26), on 5 November 2026. It is a ReShade add-on by HDRgameAnalysis, built on ShortFuse's RenoDX. It lowers the raised black level of the game's HDR and adds sliders for peak brightness, paper white and UI brightness. Alone it needs ReShade and HDR on. Next to AtmosphereMod it does nothing until one setting changes, and this guide says why.

touches add-on files apply edits AtmosphereMod's settings: InjectGraphicsRootSignature under [ATMOSPHEREMOD] in ReShade.ini, from 1 to 0. It does so only when AtmosphereMod is installed, injects, and puts its parameters in the same place as RenoDX. The first time, it keeps the value it replaced in compatdata/2537590/flightsim-on-linux-backup/renodx-hdr, and this puts it back:

~/flightsim-on-linux/bin/flightsim-on-linux addon undo renodx-hdr

Get it

The mod is free and has one source, its page on Nexus Mods, which you open in a browser. No command here can fetch it. Download the zip from the Files tab.

  • The zip that was tested has sha256 226df85c594e8ef6cfb4d416d2bb20d598b32e927d60f6f0a914a0605c3b4af2. It holds README.txt, LICENSE.txt and renodx-msfs2024.addon64.
  • renodx-msfs2024.addon64 has sha256 304008e72d2fa6a9efe23bea527dec79525ae82decd7c16ef0c36bb27eeecb7e. ReShade logs it as Registered add-on "RenoDX" v0.2026.1101.238.

The licence is MIT: the RenoDX framework is copyright 2025 Carlos Lopez Jr. (ShortFuse) and the mod is copyright 2026 HDRgameAnalysis. The author tested it on the Microsoft Store version 1.9.21.0. The test here was the Steam version. The README warns that a game update can change the game's shaders and stop the mod until it is updated.

Install it

Install ReShade first, version 6.8.0 or newer, with add-on support. The simulator has to be closed. Without a file, the command prints where to get the mod:

~/flightsim-on-linux/bin/flightsim-on-linux addon install renodx-hdr

Then give it the zip you downloaded, or the .addon64 inside it:

~/flightsim-on-linux/bin/flightsim-on-linux addon install renodx-hdr /path/to/the-zip

It checks the sha256 of the .addon64, so a re-zipped copy of the same file is fine and another version is not: it is refused, and nothing is installed. It also refuses while the simulator runs, when ReShade's dxgi.dll is not in the simulator's folder, and when another renodx-*.addon64 is there, because the mod's README allows no other RenoDX add-on beside it. Then it copies renodx-msfs2024.addon64 into the simulator's folder, beside dxgi.dll.

HDR has to be on before the simulator starts, because the game picks HDR or SDR at startup. On the test machine ReShade.log showed the swap chain in hdr10_pq.

Make it run

Without AtmosphereMod there is nothing to fix:

~/flightsim-on-linux/bin/flightsim-on-linux addon apply renodx-hdr

says so, changes nothing and runs the check. With AtmosphereMod 0.5.1 as its installer leaves it, the mod loads, finds its two shaders and replaces neither. Here is why.

  • RenoDX replaces two pixel shaders, 0x6bc6b2f3 (ph_2d_HDR10) and 0x5244e47d (ph_tonemapping). They belong to the simulator's global graphics root signature, the one with 23 parameters.
  • With InjectGraphicsRootSignature=1, AtmosphereMod adds to that root signature the root constants b0 space50 x16 and a root descriptor u0 space50. RenoDX puts its own constant buffer at b13 space50, the same register space.
  • ReShade 6.8.0 hands the root signature to the add-ons one after another, in the order they loaded, and each gets it as the one before changed it. ReShade.log shows AtmosphereMod loading before RenoDX, so RenoDX meets a root signature that already uses space 50 and gives up on it. The log shows Params not created and Failed to replace pipeline, and the image doesn't change.

Three runs on 5 November 2026 tell the cause from the other candidates:

RunAtmosphereModWhat ReShade.log shows
11:51Official, space 50, injection onEvery replacement fails.
15:49Official, InjectGraphicsRootSignature=0will insert cbuffer 13 at root_index 23, 7 lines Replacing pipeline for 0x6bc6b2f3, 2 for 0x5244e47d, no Failed to replace pipeline.
16:20Private build in space 51, injection onwill insert cbuffer 13 at root_index 25, the same 7 and 2 replacements, no Failed to replace pipeline.

What decides is the space they share, not the number of parameters. Params not created is not the line to look for: it appears in the two runs that worked as well. Failed to replace pipeline is.

apply turns the injection off when AtmosphereMod is installed, InjectGraphicsRootSignature is 1, and its parameters are in space 50. The space comes from logs/layouts.txt in AtmosphereMod's data folder, where a line like [23] root constants b0 space50 x16 dwords is AtmosphereMod's own parameters. It believes that file only when it is newer than the AtmosphereMod install. With no file, or an older one, it assumes space 50, the official build's. It changes that one line and keeps every other line and the file's line endings. When any of the three conditions fails, it changes nothing and says which.

What it costs

With the injection off, AtmosphereMod can't build the replacement of its ps_deferredRendering pass, which needs the injected root signature. Its events.log says failed to create replacement graphics pipeline for pixel shader ... (is InjectGraphicsRootSignature on?). In the run at 15:49 the vkd3d-proton log had 8 errors, dxil-spirv: Failed to remap UAV 50:0, and they are the 8 failures of that pass. That pass is AtmosphereMod's haze over the ground, which goes back to the simulator's own. The sky and the clouds keep the mod.

AtmosphereMod's installer sets the value back to 1 every time it runs, which is after every simulator update. Run apply again after each one. The check fails when you forget.

Keep both at full effect

The two mods clash only because they use the same register space. With AtmosphereMod's space moved off 50, both run with the injection on. That takes two constants, kModSpace in addon/src/atmosphere_mod.cpp and MOD_SPACE in tools/patch_dxil.py, which patches the shaders the installer makes. On 5 November 2026, at 16:20, a build of release 0.5.1 with both set to 51 ran with RenoDX: RenoDX logged will insert cbuffer 13 at root_index 25, AtmosphereMod made 254 replacements, 8 of them in ps_deferredRendering, none failed, and its layouts.txt showed b0 space51 x16.

Section 1c of AtmosphereMod's licence lets you build and run a version with your own changes for private use. Section 2b forbids publishing or sharing a modified version, or a work based on its source. So this repository ships no patch, script or binary for it, and this guide leaves the building to you. The cost is upkeep: every AtmosphereMod update needs the change made again on the new source, and running the official installer puts space 50 back, after which RenoDX fails without a word on the screen. The check catches that, because layouts.txt is then older than the install and space 50 is assumed. Issue 22 on AtmosphereMod's GitHub asks its author to make the space a setting, with 50 as the default, so the build would no longer be needed.

Start it

There is nothing to start. The add-on loads with the simulator. Press Home to open ReShade and set everything in its RenoDX tab, as the mod's README says.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check renodx-hdr

It prints five lines, each starting with ok or FAIL, and a sixth once there is a log to read, and it changes nothing. The five are:

  • ReShade's dxgi.dll is in the simulator's folder;
  • renodx-msfs2024.addon64 is there (one line), and its sha256 is the tested one (another line). Another hash fails and says the add-on is untested with that file;
  • no other RenoDX add-on is there;
  • if AtmosphereMod is installed: it passes when InjectGraphicsRootSignature is 0, or when layouts.txt shows AtmosphereMod's parameters outside space 50, and fails otherwise, with the command to run. If AtmosphereMod is not installed, the line says nothing clashes.

The sixth line comes from ReShade.log, when it shows RenoDX registered. It fails on Failed to replace pipeline, and it passes on will insert cbuffer, with the root index. The log is the last run's, so the check reads it only when it is newer than the add-on files, AtmosphereMod's install and the last apply. Otherwise the line says the log is older than the last change, and the way to settle it is to start the simulator once and run the check again.

Known problems

  • The fix needs the injection off, and that takes AtmosphereMod's ground haze with it, unless you run AtmosphereMod from a private build as the section above describes.
  • A simulator update can change the shaders RenoDX looks for, and the mod stops until its author updates it.
  • The result was judged by eye on an HDR screen. The picture itself was not measured, and neither was the frame rate.
  • The mod's README allows no other RenoDX add-on in the same folder, its DevKit included.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo renodx-hdr

This puts InjectGraphicsRootSignature back to the value it had before the first apply, one line only, and nothing else in ReShade.ini changes. Without a saved value it says there is nothing to undo. If AtmosphereMod's section is no longer in the file, it writes nothing. The add-on itself stays. To remove it, delete renodx-msfs2024.addon64 from the simulator's folder, and its section in ReShade.ini if you want that gone too.
