title: TriTriSim Hub description: How to run the TriTriSim Hub in MSFS 2024's prefix under Proton: why it crashes at start, the oletr.dll stand-in and the one import name changed in its executable, the menu entry that patches it again after each update, and how to undo it. ---

TriTriSim Hub

Tested with TriTriSim Hub 1.2.2 on 14 October 2026. It installs like any Windows program, but it crashed at start in 5 of 7 tries until a stand-in DLL sat next to it and its executable imported that DLL. So this fix changes a file of the add-on.

touches add-on files The fix changes one name inside tritrisim-hub.exe, from ole32.dll to oletr.dll, same length, and adds oletr.dll beside it. A copy of the original executable is kept in compatdata/2537590/flightsim-on-linux-backup/tritrisim-hub/tritrisim-hub.exe.orig, and this puts the name back and removes the stand-in:

~/flightsim-on-linux/bin/flightsim-on-linux addon undo tritrisim-hub

Get it

The TriTriSim Hub is a Tauri program whose window is a WebView2. Its Windows installer used here was TriTriSim Hub_1.2.2_x64-setup.exe, an NSIS setup of about 3.2 MB. Where it is downloaded from and what it costs aren't recorded here; get it from TriTriSim.

Install it

Close the simulator and every program in its prefix, and run nothing else while the installer works. The ground rules explain why. Then give the installer to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install tritrisim-hub ~/Downloads/"TriTriSim Hub_1.2.2_x64-setup.exe"

The command refuses to start while the simulator runs or any program is open in the prefix, and names those programs. It then runs the installer in the simulator's prefix. On the test machine the installer needed no setting of its own. A WebView2 area that stays grey or white under the Wayland driver is a different matter, covered in the Proton FS2024 guide.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply tritrisim-hub

The crash was an invalid read inside ole32, 0x6d bytes into RevokeDragDrop, called from the Hub's window procedure. A trace of the OLE calls showed what happens. The WebView2 process, msedgewebview2.exe, registers drag and drop on the child window it draws, with a pointer from its own memory. The Hub calls RevokeDragDrop on that same window. Wine keeps the pointer in a window property and follows it in RevokeDragDrop without asking which process it came from. If the address doesn't exist in the Hub, the Hub crashes. If it does exist by chance, nothing happens, which is why the crash came and went. Wine already refuses the opposite call, RegisterDragDrop on another process's window.

The fix has two parts:

  • oletr.dll, a stand-in built on your machine with MinGW. It has the 8 ole32 functions that the Hub imports. Seven go on to the system ole32, and its own RevokeDragDrop answers DRAGDROP_E_NOTREGISTERED when the window belongs to another process.
  • The import name in tritrisim-hub.exe, changed to oletr.dll. A stand-in named ole32.dll next to the program did not load. ole32 is on the prefix's list of DLLs that always come from the system (KnownDLLs in system.reg), so the Hub has to ask for another name.

With the stand-in the test machine had 0 crashes in 3 starts, and the RevokeDragDrop calls that reach Wine dropped from 3 or 4 to 2. apply refuses to touch an executable that doesn't hold exactly one ole32.dll import name (or exactly one oletr.dll, when it is already patched), and says so.

A Hub update brings the original executable back. The launch script changes the name again on every start, when the Hub isn't running, so an update needs nothing from you. apply does the same by hand. The backup of the original is renewed each time, so it is always the version before the last change.

The stand-in needs x86_64-w64-mingw32-gcc: install mingw-w64-gcc (Arch), gcc-mingw-w64-x86-64 (Debian, Ubuntu) or mingw64-gcc (Fedora). apply builds the stand-in first, and changes the executable only if that worked: an executable pointing at an oletr.dll that isn't there would not start.

apply and undo refuse while the Hub is open, because they change its executable. Close it first; its menu entry has a Close action. The new executable is written to a temporary file in the same folder and then swapped in, so a run that stops half way leaves the original whole.

Start it

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut tritrisim-hub

This writes an entry called "TriTriSim Hub" in your application menu, with the Hub's own icon when 7z and magick are installed, and a "Close TriTriSim Hub" action. The entry patches the executable if it needs it, then starts the Hub in the simulator's prefix. With the simulator running it starts the Hub inside the simulator's container, and with the Hub already open it says so and touches nothing. The action asks all of the Hub's processes to end, the way a polite kill does, and never uses kill -9. Close the Hub before you start the simulator or run an installer, since a program left open in the prefix holds it.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check tritrisim-hub

It prints four lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • the executable imports oletr.dll once and ole32.dll not at all;
  • oletr.dll beside it is, byte for byte, the stand-in built from this repository;
  • Proton's shell32.dll and explorer.exe are the ones Proton FS2024 built with the tray icon fix. The Hub asks Windows where its tray icon is on every click and drops the click when it gets no answer, and Wine had no answer, so the icon ignored both buttons. On 2 November 2026, with a build that has the fix, a right-click opened the menu with Show Installer and Quit.

When the first one fails after an update, start the Hub from its menu entry or run addon apply tritrisim-hub.

Known problems

  • The mouse arrow vanishes over the Hub's window. Resizing the window and bringing the arrow back over it shows it again. Wine's X11 driver didn't change it, since outside the simulator's container the Hub already uses it, and turning the Wayland driver off for the Hub (winewayland.drv=d) made no difference. Running the Hub inside gamescope was not tried. The Fenix installer had the same defect together with the keyboard, and gamescope solved it there.
  • An update brings the original executable back until the Hub is started from its menu entry or the fix is applied again.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo tritrisim-hub
~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut tritrisim-hub --remove

The first changes the import name back and removes oletr.dll. If the Hub updated since the fix, it works on the new executable, so a new version isn't replaced by an old one. The copy of the original stays in the backup folder. Without the fix the Hub crashes at start again, as it did before. The second takes out the menu entry.
