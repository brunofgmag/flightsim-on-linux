title: Proton FS2024 description: What Proton FS2024 is, why the Fenix, FSLabs, Active Sky, AutoFPS, the Glass Cockpit DLSS Fix and the WebView2 add-ons need it, how this project builds, checks and swaps it, and how to undo it. ---

Proton FS2024

One Proton for the simulator and its add-ons: a Proton-CachyOS release with 14 Wine modules rebuilt, the eleven of the fenix-a320-linux-patch overlay and three for this project's fixes, plus vkd3d-proton's d3d12core.dll with two fixes from this project. Three of the overlay's modules, wineserver, win32u and d2d1, also carry fixes of ours. It runs the simulator and every other add-on in the prefix, so the fixes reach all of them. Steam lists it as Proton FS2024, and each new build replaces the same folder, so you pick it once.

Why the simulator needs a special Proton

Most add-on problems can be fixed inside the prefix. A few are bugs in Wine itself, and those need a rebuilt Wine:

ModuleWhat goes wrong without itSource
11 modules, among them ntdll, kernelbase, crypt32, d2d1, dwriteThe Fenix runner spins at full CPU without opening a window, the aircraft won't power up, and the Fenix displays draw wrong.fenix-a320-linux-patch v0.1.0-preview.7, by its own authors
d2d1, one of the overlay's 11The Fenix displays grow by about 4.6 MB a second, their frame rate drops within minutes, and then they freeze. wine-cachyos never frees one array of each path figure it destroys, which upstream Wine does free. Separately, a path with NaN coordinates sent Direct2D into a loop that never ended, and a path whose Bézier curves lie on top of each other spent seconds splitting them, so the displays stalled whenever the Fenix drew one.this project, on top of the overlay
wineserver, one of the overlay's 11The simulator stutters in a steady rhythm, worst while ChasePlane is running. When a program reads another program's memory, the wineserver uses process_vm_readv, which stops nobody. After its first EPERM from any process, it switched that off for good and fell back to ptrace, which stops the main thread of the program being read on every read. ChasePlane reads the simulator hundreds of times a second, and the simulator's main thread stood still for up to 300 ms of every second. Upstream Wine has the same behaviour.this project, on top of the overlay
win32u, one of the overlay's 11With the Wayland driver, the WebView2 part of SayIntentions, the GSX flightsim.to window and REX Atmos Core stay grey or white. Their content comes from a second process, and Wine dropped whatever that process drew. In GPU display mode the Fenix display process also quits a few seconds after it starts, because it can't wait on the D3D12 fence the simulator shares with it. Every process that has used such a fence also crashed while it exited, because the NVIDIA driver's cleanup ran while Wine's fence thread was still waiting on the GPU, and the Fenix display left a core dump each time.this project, on top of the overlay
gdiplusFSLabs displays are covered in glow, and the MCDU and clock letters lose their right side. Active Sky stops at its own error screen, because GDI+ can't find Microsoft Sans Serif or Calibri once font substitution is involved.this project; the font fix is upstream Wine commit e6e9d7627c (Wine 11.17), which wine-cachyos doesn't have yet
shell32Programs built on H.NotifyIcon, such as AutoFPS with "Close to Tray", crash on start.this project
d3d12core, from vkd3d-protonThe Glass Cockpit DLSS Fix, a ReShade add-on that takes the DLSS blur off the cockpit displays, skips every display draw. It only redraws a display when the root signature bound at draw time is the same object the display's pipeline was created with. Windows hands back the object it already has when a program creates an identical root signature again. vkd3d-proton made a new one every time, and the simulator created the root signature of the PMDG 777 displays 13 times. Once that was fixed, the add-on still skipped about 3.5% of the draws. In a large descriptor heap, the addresses vkd3d-proton hands out for the last quarter of the descriptors lie past the end of the heap's own memory, and the add-on's read of them fails. Now the heap's memory covers every address it hands out; a heap of a million descriptors grows from about 24 MB to 32 MB.this project
winewaylandOn some displays under KWin 6.8, Wine windows go black or see-through, with only the near-white pixels left. We saw it on a 4K HDMI TV at 125% scale and never on the second monitor. Separately, the simulator's arrow froze in place until you switched windows: the simulator keeps its cursor clipped to its window and hides it now and then, and the driver answered that with a pointer lock, which ignores where the mouse is. Now a hidden cursor clipped to the whole window is only kept inside the window, so it keeps moving. Under KWin 6.8 a pointer lock or confinement also changes only when the window commits, and the simulator, which draws through Vulkan on a separate surface, hardly ever commits its window: a lock it released stayed on and froze the arrow until you switched windows. The driver now commits the window every time it changes a lock or a confinement. Last, while you drag the ChasePlane camera with the middle button, the simulator clips the cursor to a single pixel and lets it go every 30 ms. On Windows that keeps the cursor on that pixel; on Wayland a confinement only holds while the pointer is already inside it, so the arrow drifted off the screen. Now the driver moves the pointer onto the clip rectangle before it confines it. At 125% scale that one-pixel clip also came out of the driver's rounding as a region with no width, which confines nothing (849 of them in one drag), and the pointer could land on the region's last edge, which is outside it. Now every region is at least one pixel wide and tall, and the pointer goes inside it.this project

The Proton also carries a user_settings.py with the nine settings the overlay's installer writes, plus cef_browser.exe in WINE_TRACK_WRITECOPY. Without that last one the FSLabs EFB browser crashes when it starts.

What else WebView2 add-ons need

The win32u fix only helps when WebView2 draws in software. With its default GPU drawing, the page stays invisible even with the fix. A WebView2 policy in the prefix switches every WebView2 program to software without changing the programs themselves:

~/flightsim-on-linux/bin/flightsim-on-linux run reg add 'HKCU\Software\Policies\Microsoft\Edge\WebView2\AdditionalBrowserArguments' /v '*' /t REG_SZ /d '--in-process-gpu --disable-gpu --disable-gpu-compositing --disable-software-rasterizer' /f

Run it with the simulator open. Each program reads the policy when its WebView2 starts, so reopen the program afterwards. --disable-software-rasterizer keeps WebView2 off the GPU. Without it, a program that can't see a Vulkan driver crashes the moment its WebView2 starts.

A value named after a program (for example SayIntentionsAI.exe) replaces the * value for that program instead of adding to it, so it has to repeat the four options. GSX ignores the policy altogether. It does take the same options from the WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS environment variable, which has to be set for GSX alone, because the variable also overrides every other program's policy.

What else the Fenix GPU displays need

The Fenix draws its displays either on the CPU or on the GPU. GPU mode needs the two win32u fence fixes above, and also a DXVK with three fixes of its own in the Fenix deps folder: the adapter LUID of a shared resource, a keyed mutex that waits for what the other side drew, and two timeout fixes from upstream DXVK. bin/flightsim-on-linux dxvk build builds and tests it, and the Fenix guide puts it in place.

How it is built

bin/flightsim-on-linux proton build runs proton/build-proton-fs2024.sh. Close the simulator first. The build won't start while the simulator runs, because it ends by swapping the Proton the simulator uses. The script:

  1. downloads the Proton-CachyOS release and checks it against the release's own sha512;
  2. downloads the overlay patch from the overlay's tagged source and checks a pinned sha256;
  3. asks GitHub which wine-cachyos commit the release was built from, and fetches only that commit;
  4. applies the sixteen patches and stops at the first one that doesn't apply cleanly;
  5. refuses to continue if the wineserver protocol changed, because the release's 32-bit parts would stop talking to it;
  6. compiles the 14 modules, checks that none needs a system library the original didn't, and swaps them into a copy of the release;
  7. reads which vkd3d-proton commit the release ships, fetches only that commit, applies the two vkd3d-proton patches and swaps the d3d12core.dll it compiles into the same copy. If the release patches vkd3d-proton itself, the script stops before it fetches any source, because the build would drop those patches;
  8. starts a Windows process inside the Steam Linux Runtime the release asks for;
  9. runs the checks below on the result, and stops if one fails;
  10. only then installs it as compatibilitytools.d/Proton-FS2024. A build already there moves to ~/.cache/flightsim-on-linux/previous/Proton-FS2024, and the one that was there before it is deleted. The build folder, about 1.5 GB, is deleted too; when the build stops before this step, it stays, and the script prints the command that removes it.

Steam keeps the simulator on Proton FS2024 from one build to the next, so the next start of the simulator runs the new build. To go back, close the simulator and swap the two folders. Each build has an fs2024-build.txt with the release hash, the Wine and vkd3d-proton commits and a hash for every patch and module, so you can tell exactly what you are running.

Only cachyos-11.0-20261005-slr has been verified. You can pass another cachyos-11 release, proton build cachyos-11.0-…, and the script stops if a patch no longer applies. The overlay's authors publish a new variant when CachyOS moves to a Wine the patch doesn't fit.

How it is checked

bin/flightsim-on-linux proton check creates a throwaway prefix, compiles fifteen small Windows programs, plus a small Linux one where libei and libsystemd are installed, and runs seventeen checks with the Proton the simulator uses. The build runs the same checks before it installs anything.

CheckPasses when
Overlay loaderA program named Fenix.exe sees KERNEL32.DLL and KERNELBASE.dll spelled as on Windows. The probe is the overlay's own loader-case-probe.c.
Tray icon by GUIDA tray icon can be changed and removed by its GUID alone. Needs an X11 display; without one the check says it could not run.
GDI+ path gradientFocus, blend and preset colours land where Windows puts them.
GDI+ centred textAn "M" centred on x = 100 is centred within 1.5 pixels. Stock Wine draws it about 4 pixels to the right.
Direct2D memoryBuilding and releasing 300,000 path geometries leaves less than 8 bytes behind for each one. Stock Proton-CachyOS leaves 54.
Direct2D with NaNClosing a path whose points are all NaN returns within 15 seconds. On stock Proton-CachyOS it never returns.
Direct2D with overlapping curvesClosing a path of two identical figures, each with two overlapping Bézier curves, takes less than a second. Stock Proton-CachyOS took 1.8 seconds here on the test machine.
Memory read after an EPERMA program reads another process 2,000 times, makes the wineserver get an EPERM from a third process that refuses to be read, and reads 2,000 times again. The main thread of the process being read is never stopped by the second round. Without the fix it is stopped on almost every read, 1,996 times out of 2,000 on the test machine. The EPERM comes from Yama, so the check says it could not run where /proc/sys/kernel/yama/ptrace_scope is not 1.
Shared D3D12 fenceA program creates a shared D3D12 fence and starts a second process. That process opens the fence with OpenSharedFence, sees the first value, receives the value the first one signals and signals its own, and the fence ends at 40. It needs a Vulkan GPU. With an integrated and a discrete GPU the check uses the discrete one; if it can't tell which to use, or vulkaninfo is missing, it says it could not run. On stock Proton-CachyOS the second process stops at OpenSharedFence and the fence stays at 10.
Exit after a shared fenceBoth processes of that program exit with status 0 and leave no core dump of this Proton in coredumpctl. A crash while a process exits doesn't change its exit status, so the dumps are the only trace. Needs systemd-coredump; without it the check says it could not run. It is a separate check so a failure says which fix is missing: a Proton without the exit fix passes the fence value check and fails this one.
Identical root signatureA program creates the same root signature twice from one blob and once from a copy of that blob, and gets the same object all three times. A different blob gives another object, and once the last reference is gone the same blob gives a new object with one reference. It runs on the GPU the fence check picks, and says it could not run where that check can't. On stock Proton-CachyOS each of the first three calls returns its own object.
Descriptor heap addressesA program creates 8 descriptor heaps of 65,536, 100,000 and 1,000,000 descriptors each, CPU-only and shader-visible, and checks with VirtualQuery that every address a heap hands out is readable memory of that heap's own allocation. It runs on the same GPU. On stock Proton-CachyOS 7 of the 48 heaps failed on the test machine; the count changes from run to run, because the check only fails when the memory after a heap belongs to something else.
Hidden cursor clipped to its windowUnder the Wayland driver, a program hides its cursor and clips it first to its whole window, then to a 20-pixel square in the middle. The driver only confines the pointer in the first case and still locks it in the second. Without the fix it locks it in both. Needs a Wayland session; the check reads the driver's own log, and if the test window never gets the focus, or loses it before the test ends, it tries three times and then says it could not run.
Released pointer constraint under KWin 6.8Under the Wayland driver, a program repeats the cursor calls the simulator made when its arrow froze: it hides the cursor, clips it to its window and to a single pixel a few times, shows it and lets it go. The check reads the Wayland protocol the driver sent (WAYLAND_DEBUG=1) and passes when every lock or confinement released while the window is still open is followed by a commit of the window. Without the fix none is. Needs a Wayland session; if the test window never gets the focus, or loses it before the test ends, it tries three times and then says it could not run.
One-pixel clip at 125% scaleThe check starts its own KWin with a virtual screen at 125% scale and a virtual pointer, and a program under the Wayland driver clips the cursor to one pixel five times in a row, each time one pixel further along, and then to an 8-pixel square. The check reads the Wayland protocol the driver sent (WAYLAND_DEBUG=1) and passes when every confinement region is at least one pixel wide and tall. Without the fix the third pixel gives a region 0 pixels wide and 0 tall. The KWin has its own settings folder and its own message bus, so the check doesn't touch your pointer or your KWin settings, and it needs no Wayland session of yours. It says it could not run where kwin_wayland, dbus-run-session or busctl is missing, or where libei and libsystemd were missing when the check programs were built.
Pointer moved inside a small clipSame private KWin session, same program, same protocol log. After each confinement, the driver has to warp the pointer to a point inside the confinement region. Without the one-pixel fix the warp for the 8-pixel square lands on the region's edge: the region ends at 86 and the warp goes to 86.
Child window from another processUnder the Wayland driver, a second process draws a red child window with a yellow square inside the first program's blue window, and the first program reads red and yellow back. Needs a Wayland session; without one the check says it could not run.

Against stock Proton-CachyOS cachyos-11.0-20261005-slr, all twelve checks that existed before the commit check fail; the commit check and the two small-clip checks have not been run against it. On 2026-10-21 the two vkd3d-proton checks failed on it as well, and a build with only the root signature fix failed only the descriptor heap check. Each patch also has its own check that fails when only that patch is left out. Without the shell32 patch only the tray check fails, and without the win32u child-window patch only the child-window check fails. Without the d2d1 array fix only the memory check fails, and without the NaN fix only the NaN check fails. A build without the winewayland cursor fix fails only the cursor check, a build without the commit fix fails only the commit check, and a build without the one-pixel fix fails only the two small-clip checks. That is how we know each check catches what it claims to.

The two winewayland fixes for small clips, the one that moves the pointer onto the clip and the one that keeps a one-pixel clip from becoming an empty region, are checked in a private KWin session that the check starts itself, so it never has to hold your real pointer. On 2026-10-19 a build without the one-pixel fix failed those two checks and nothing else, and the installed Proton FS2024 passed all fifteen. Before the checks existed we tried the pointer fix by hand in an isolated KWin session, with the clip pixel 200 pixels away from the pointer: the arrow stayed on the pixel with the fix and moved freely without it.

The winewayland fix for black windows has no automatic check here. It changes what the compositor receives, and a program running inside Wine can't read that back. We checked it by eye on the TV where Wine windows broke: a test window whose left half sends 0x00 in the unused byte and whose right half sends 0xFF showed only its right half before the fix and both halves after.

What has been measured in flight

On 2026-10-18 the Fenix displays ran in GPU mode for 18 minutes on a Proton built from the same release with the same eleven patches. The display process stayed at about 560 MB, its drawing thread at about 41% of a core, and the frame rate didn't drop. Without the d2d1 fix, the same displays passed 4.9 GB within 20 minutes, the drawing thread climbed to 90% of a core, and the frame rate collapsed.

On the same day, with ChasePlane running, the wineserver used to stop the simulator's main thread 187 to 445 times a second, 172 ms of every second in all and up to 304 ms while ChasePlane was busy. On a build with the wineserver fix it stopped it 4.3 times a second, 3 ms of every second, and the periodic spikes left the frame-time graph. The simulator's arrow also stopped freezing on the first click after the cursor fix.

On 2026-10-19, with the one-pixel fix, the driver logged 1,256 one-pixel confinements during ChasePlane camera drags on the 125% TV, none of them empty and each followed by a warp inside it, and the arrow stayed still on the drag. The day before, without it, one drag gave 849 empty ones.

On 2026-10-20, with both vkd3d-proton fixes and the PMDG 777, the Glass Cockpit DLSS Fix redrew 25,707 of 25,716 display draws; the other 9 were waiting for a shader to compile. On NVIDIA the add-on also needs descriptor_tracking=1 in the [debug] section of its glass-cockpit-dlss-fix.ini. The evening before, with only the root signature fix, it skipped 5,339 of 154,228, and one display flickered.

Those Protons came from the author's own build script, not from this repository's. CPU display mode uses the same d2d1 code but hasn't been flown with the fix, and nobody has logged a full flight on a build made by this repository yet.

Undo

Pick another Proton under Compatibility in the simulator's Properties, then delete the Proton-FS2024 folder from ~/.local/share/Steam/compatibilitytools.d/. The build cache and the previous build live in ~/.cache/flightsim-on-linux and can go too. To drop the WebView2 policy, run the same reg command with delete in place of add and without /t and /d.
