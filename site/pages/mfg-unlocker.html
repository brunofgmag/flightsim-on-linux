title: MFG Unlocker description: How to run the MFG Unlocker fork 1.7.1-xmx.2 in MSFS 2024 under Proton FS2024 on an RTX 40 card: the pinned downloads, XMX mode with Intel's two XeSS files, XeLL sleep, the launch options and the config keys. ---

MFG Unlocker

Tested with the MFG Unlocker fork 1.7.1-xmx.2 on 12 November 2026, on an RTX 4080 with Proton FS2024 and ReShade as dxgi.dll. It adds multi frame generation, 3x to 6x, to the simulator's DLSS frame generation on an RTX 40 card, with a menu that opens on Backspace. The fork already carries what Wine needs, and it adds XMX mode, where Intel's XeFG model draws the generated frames. This add-on installs the fork and sets the config keys it needs.

touches add-on files The install writes the fork's DLL as version.dll in the simulator's folder and two of Intel's libraries in RTXMFG-XeSS beside it. apply edits the mod's own config file, RTXMFG-Universal.json, in the same folder. The first time, it keeps the original in compatdata/2537590/flightsim-on-linux-backup/mfg-unlocker, and this puts it back and removes the three files:

~/flightsim-on-linux/bin/flightsim-on-linux addon undo mfg-unlocker

What the fork adds

The fork is brunofgmag/MFG-Unlocker, a fork of dashdogy's MFG Unlocker 1.7.1. It is free and MIT-licensed (copyright 2026 Michael Robles). It adds two things to upstream: fixes that let the mod run under Proton and Wine, and the XMX generation mode from mavismmg/MFGAdaUnlock-RenoDx.

  • XMX runs Intel's XeFG model inside the game's own DLSS frame generation, on RTX 40 and RTX 50 cards. DLSS frame generation still presents the frames and keeps Reflex. XeFG only draws the generated frames, and NVIDIA's generator is never created. That left about 940 MB more video memory to the simulator at 4K. XMX stays off on RTX 30 and RTX 20 cards, and while XeMFG standalone is on.
  • XeLL sleep sends the game's Reflex sleep to Intel's XeLL while XMX generates. Under Proton it also keeps the low latency mode off in vkd3d-proton, so vkd3d-proton keeps its own queue limit of two frames. With it on you don't need VKD3D_DISABLE_EXTENSIONS=VK_NV_low_latency2. On the test machine, in a flight on 12 November 2026 with that extension on, the real frame went from 42.8 ms to 33.3 ms the moment XeLL sleep was ticked, and the video memory stayed steady. Without XeLL sleep and with the extension on, the Reflex sleep loop pulled a 30 fps base down to about 23 fps.
  • The Proton fixes. The menu and the adapter-parent route work with ReShade loaded as dxgi.dll. DLSS 5 compiles its compute shaders with Wine's D3DCompile and opens its provider when Wine reports PAGE_WRITECOPY. DLSS 5 accepts depth, motion vectors and exposure with mips, as the simulator sends them. Earlier versions of this add-on changed those places in upstream's file as byte patches at install. The fork has them in its source, so the add-on patches nothing any more.

The fork's README, at the top of its repository page, says the same. Its builds are on its own releases page, and upstream's release has neither the fixes nor XMX.

Get it

You don't need to download anything yourself: the install command does, and checks every hash. This repository ships no DLL.

  • The fork's zip, MFGUnlocker-v1.7.1-xmx.2.zip, has sha256 2d5d36960df058037f596075b6509935624aaaacefd658c4ebe7970061f73944.
  • MFGUnlocker.dll inside it, the only file in the zip, has sha256 8606cc4a76df92a31cc4d751177134f7ec447921e756a35608cdd24436a52e32. A version.dll with this hash counts as this add-on's.
  • Intel's XeSS SDK 3.0.2, XeSS_SDK_3.0.2.zip, has sha256 88b8a373f30e33f3558a77a93e634f11b8132fc3047ea1a8edeead32b8471990. It is about 77 MB, and the install takes two files from its bin folder:
    • libxess_fg.dll, version 1.3.1.78, with sha256 ec5e0c65e075570c6ede72618bb666d0be0c2e10b2ea9762c0fe8cb8e375ab27. XMX needs that version: with another one, NVIDIA's generator keeps running.
    • libxell.dll, with sha256 d2030dcd694fda8f2ec7e044b13e6db8f0b56d4ba9113a5efad334e3f3ded8c7.

The fork's DLL embeds XeSS frame generation program data derived from Intel's SDK. That data is Intel's work, is not covered by the MIT licence and stays under Intel's licence terms. The fork's repository has the notice.

Install it

Install ReShade first: the fork was measured with it, and this guide has not been tried without it. The simulator has to be closed.

~/flightsim-on-linux/bin/flightsim-on-linux addon install mfg-unlocker

The command downloads the fork's zip from https://github.com/brunofgmag/MFG-Unlocker/releases/download/v1.7.1-xmx.2/MFGUnlocker-v1.7.1-xmx.2.zip with curl, checks its sha256 and keeps it in ~/.cache/flightsim-on-linux/downloads. Then it does the same with https://github.com/intel/xess/releases/download/v3.0.2/XeSS_SDK_3.0.2.zip. It reads MFGUnlocker.dll and the two Intel libraries from the zips and checks the sha256 of each. Only then does it write anything: the two libraries into RTXMFG-XeSS in the simulator's folder, then the DLL as version.dll beside FlightSimulator2024.exe. Any file that doesn't match stops it before anything is written. The hashes are pinned because these are the files the add-on was tested with.

If you already downloaded the fork's zip, give it to the command: addon install mfg-unlocker /path/to/MFGUnlocker-v1.7.1-xmx.2.zip. It must be the same release, and the command still fetches Intel's SDK.

A version.dll that is not the fork's, or a libxess_fg.dll or libxell.dll in RTXMFG-XeSS that is not Intel's file above, stops the install. The command names the file and its sha256, and nothing here overwrites it: another mod may use that name. Files you keep in RTXMFG-XeSS stay. Files that already match are left alone, and the install writes only what is missing.

Make it run

The order matters, because the mod writes its config file the first time it runs and apply edits that file:

  1. Install the add-on, as above.
  2. Add the launch options below in Steam.
  3. Start the simulator once and close it. The first start compiles shaders and stutters.
  4. Run ~/flightsim-on-linux/bin/flightsim-on-linux addon apply mfg-unlocker.
  5. Start the simulator again. "xmx" takes effect at a start of the simulator, so the first start after apply is the first one with XMX.

The launch options

Steam keeps the launch options of the simulator in localconfig.vdf and rewrites that file, so nothing here edits it. apply and check read the options and say which parts are missing. Add them in Steam, in the simulator's properties, before %command%:

WINEDLLOVERRIDES="version=n,b" PROTON_NVIDIA_NVCUDA=1 PROTON_DLSS_UPGRADE=1 %command%
  • WINEDLLOVERRIDES="version=n,b": Wine would load its own version.dll and never the file in the simulator's folder. If the line already has WINEDLLOVERRIDES, add version to it: names with the same mode go together, as in dxgi,version=n,b, and entries with different modes are separated by a semicolon.
  • PROTON_NVIDIA_NVCUDA=1: the mod takes the RTX 40 route only when CUDA answers with compute capability 8.9, and the RTX 30 and RTX 50 routes also ask CUDA. Proton leaves CUDA off without this. Proton FS2024 honours it. Without it the log has capability=0.0 verified=0 and route=pending ready=0.
  • PROTON_DLSS_UPGRADE=1: Proton then puts the newest DLSS frame generation in the prefix. The mod was tested with that copy, and the simulator's own nvngx_dlssg.dll stays as it is.

Your other options can stay. The launch options guide says what each of the others does, and which ones suit which machine. Three more are worth knowing with this fork, and check doesn't look for them:

  • __GL_0xcfcfa1=0 keeps the simulator's video memory budget near 15 GB with XMX. Without it the budget fell to 13.7 to 14.4 GB, because the NVIDIA driver's background shader compile threads grow a block of memory that never shrinks. With it, on 12 November 2026, the budget slipped 79 MB in 16 minutes of flight with a camera that changed every few seconds. It is an internal setting of the NVIDIA driver 620.70.06, read from that driver's library, and it can mean something else or nothing in another version. What it costs the rest of the simulator, which loses the driver's usage-guided recompiles, was measured only as frame pace, and the pace didn't change.
  • VKD3D_SWAPCHAIN_LATENCY_FRAMES=2 lowers the swap chain queue of vkd3d-proton. With XeLL sleep on, the mod holds vkd3d-proton's low latency mode off, so its own limiter holds the queue on every Present, generated frames included. The default is 3 frames, and 2 removes one frame of it, 8.3 ms at 4x on a 120 Hz screen. On the test machine the latency felt better with 2 than with 3 in a flight on 11 November 2026, and the real frame stayed at 33.3 ms. That was a feeling, not a measurement of the latency. vkd3d-proton's own comment warns that a short queue can drop the GPU clock in some games. With 1, the game's Present waited 2.5 to 4.5 ms at the median instead of 0.06 ms, and the output left 120, though video memory was at its ceiling then too.
  • VKD3D_SWAPCHAIN_PRESENT_MODE=MAILBOX only if the picture tears. See the known problems below.

An earlier version of this guide also asked for ngx_dlss_fg_override=on in DXVK_NVAPI_DRS_SETTINGS. The add-on no longer asks for it, and XMX doesn't use NVIDIA's generator preset: the mod's overlay shows it as "Not used with XMX". Dropping it from the options of the test machine was decided on 12 November 2026, and that machine had not flown without it when this page was written.

The config keys

The mod writes RTXMFG-Universal.json in the simulator's folder when it first runs. apply sets four keys in it, changes no other byte, and when a key is missing it adds it:

  • "followGame" to false and "mode" to "fixed". The simulator asks DLSS frame generation for its dynamic mode, and in the mod's default mode, "follow game", the mod passes that on without a target frame rate and nothing is generated: the simulator's frame generation is on and the log still says presented=1. The mod only generates frames here in fixed mode.
  • "xmx" to 1, the same key the menu's Generation model writes when you pick XMX. It takes effect at the next start of the simulator.
  • "xmxXell" to 1, the key behind the menu's XeLL sleep. The mod applies it while the simulator runs.

The mod reads the number, not true. A key called "xmxStandIn" is on by default with XMX, and then the mod answers the game's frame generation request without creating NVIDIA's generator. apply leaves it as it is. The multiplier is yours: change "multiplier" in the file, or pick it in the mod's menu. 4x fixed is what the test machine runs. If the file doesn't exist yet, apply says to start the simulator once and run it again. It also refuses until version.dll and both Intel libraries are in place.

If you pick NVIDIA's generator in the menu on purpose, check fails on the "xmx" line until you set the key to 1 again.

Start it

Turn DLSS frame generation on in the simulator's graphics settings. The mod's menu appeared by itself in the simulator's main menu on the test machine, and Backspace opens and closes it. The menu is where the generation model, XeLL sleep, the mode and the multiplier change, and where the mod's other settings are.

The mod generates frames in flight and not in the menus. While the menu is up, the log stays at route=pending ready=0.

The DLSS 5 tab of the menu appears when nvngx_dlssnr.dll sits beside the simulator's executable. The DLSS 5 Neural Rendering guide says where that file comes from. The tab starts off.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check mfg-unlocker

It prints fourteen lines, each starting with ok or FAIL, and changes nothing. Before the mod has run once and written its log, it prints eleven:

  • the GPU the simulator uses is an RTX 40 series card, chosen the way the other tools of this repository choose it, through vulkaninfo;
  • version.dll in the simulator's folder is the fork's file, by its sha256;
  • libxess_fg.dll and libxell.dll in RTXMFG-XeSS are the two files of the XeSS SDK 3.0.2, by their sha256, one line each;
  • the launch options in Steam hold each of the three parts, one line for each;
  • "followGame" is false and "mode" is "fixed" in the config file, with the multiplier on the second line, and "xmx" and "xmxXell" are 1, one line each;
  • the mod's newest log, RTXMFG-flightsimulator2024-<hash>.log, has capability=8.9 verified=1, so the mod found the card through CUDA, MFG_PROXY_UI state=active, so its menu installed, and XMX runtime, so it loaded Intel's two libraries. The earlier logs, named .previous.log, are not read.

The check can't see frame generation itself. For that, fly with it on and read the log:

SIM=$(~/flightsim-on-linux/bin/flightsim-on-linux machine --json | python3 -c 'import json,sys; print(json.load(sys.stdin)["sim_install"])')
grep -E 'State heartbeat|XMX VRAM 10 s|XeLL sleep' "$(ls -t "$SIM"/RTXMFG-*.log | head -1)" | tail -5

With XMX on, the log has XMX XeLL sleep on and XMX stand-in on at the start, an XMX init line with result 0 when the simulator creates frame generation, and a XMX VRAM 10 s line every ten seconds. State heartbeat with presented=1 means nothing is generated yet.

Known problems

  • The first start after an install compiles shaders and stutters. Close the simulator and open it again before you judge.
  • Only ReShade 6.8.0 as dxgi.dll was tested, with AtmosphereMod, the Glass Cockpit DLSS Fix and RenoDX HDR loaded in it. The fork's fixes for the menu and the adapter-parent route are for ReShade as the simulator's dxgi.dll. Without ReShade the install prints a note and goes on, and the result is untried.
  • The DLSS 5 tab and the add-on of the DLSS 5 Neural Rendering guide do the same job and must not run together. The tab starts off, so with dlssnr-linux.addon64 in the folder, leave the tab off. The test ran with that add-on removed.
  • XMX works on RTX 40 and RTX 50 cards, and the add-on's check asks for an RTX 40 card because that is the card it was tested on. XMX needs libxess_fg.dll 1.3.1.78 exactly.
  • With V-Sync on in the simulator and frame generation running, the picture can tear. On the test machine on 6 November 2026, the mod, in its upstream 1.7.0 release, ran at 4x with FrameLimiter 30 and VSync 1 in UserCfg.opt and PROTON_ENABLE_WAYLAND=1 in the launch options, on a TV at 3840x2160 and 119.88 Hz. Tear lines showed in the top and bottom bands of the screen as the view turned, and VKD3D_SWAPCHAIN_PRESENT_MODE=MAILBOX before %command% stopped them. The variable is optional: apply and check don't look for it, so add it only if you see tearing. MAILBOX waits for the screen's refresh to show a frame, so it doesn't tear, but it doesn't hold the game back. FIFO as the value stops the tearing too, but FIFO holds the game until the screen refreshes. With FIFO on the test machine, the frame rate fell after a few minutes and the Steam performance monitor turned red. With MAILBOX the monitor never turned red, and the output held 120 for the five minutes measured. On a screen without VRR, a small hitch every few seconds can remain while the view turns, with the game at about 120 FPS. On the test machine it went away once VRR was on: in KDE Plasma, set Adaptive sync to Automatic in Display Configuration. With the variable, vkd3d-proton uses MAILBOX for every frame, so setting V-Sync to Off in the mod's menu has no effect. The driver has to offer MAILBOX for the game's window, or vkd3d-proton ignores the variable. On the test machine, NVIDIA driver 615.78.08 offered it for a Wayland window, which is what PROTON_ENABLE_WAYLAND=1 gives the simulator, and not for an X11 one.
  • A version.dll that another mod put in the simulator's folder blocks the install, and the check names its sha256.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo mfg-unlocker

With the simulator closed, this deletes version.dll when it is the fork's file and leaves any other. It deletes libxess_fg.dll and libxell.dll from RTXMFG-XeSS when they are Intel's files above, and leaves any other. It removes the RTXMFG-XeSS folder only when that leaves it empty. It puts RTXMFG-Universal.json back as it was before the first apply. It then lists the files the mod made in the simulator's folder, RTXMFG-* (the config, the status file, the logs and the interval tables) and RTX40MFG-UI*.ini, and deletes none of them. Delete them yourself if you want them gone.

The launch options stay as they are. Take version out of WINEDLLOVERRIDES and the other parts out of the line yourself, unless something else uses them.

Go back to upstream

Run addon undo mfg-unlocker, then copy MFGUnlocker.dll from dashdogy's release to the simulator's folder as version.dll. The launch options stay the same. Upstream's release has neither the fork's Proton fixes nor XMX and XeLL sleep, as the fork's README says, and this add-on's check will fail on the lines about the Intel files and the XMX keys. Versions of this add-on before the fork applied those fixes to upstream's 1.7.0 file as byte patches at install, listed in addons/mfg-unlocker/parts/patches.json. That file is in this repository's history and no longer in the tree, and nothing here installs upstream any more.
