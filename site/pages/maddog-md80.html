title: Maddog MD-80 description: How to install, register and run the Leonardo Fly the Maddog MD-80 in MSFS 2024 under Proton: the installer, registration through the Load Manager, .NET Framework 4.8 for the MDClient program, a native Manager for liveries and options, and what is still unproven. ---

Maddog MD-80 (Leonardo)

Tested with Fly the Maddog 20th Anniversary Edition 2.1 b283 on 22 October 2026. It needs no Proton patch of its own, but it takes several steps: register with the simulator closed, add .NET Framework 4.8 for one program, and use a native Manager, because the vendor's Manager doesn't open on Wine. It was tested on Proton FS2024. Stock Proton was not tried.

touches add-on files The native Manager writes the Maddog's own files: its liveries, layout.json, manifest.json and option files. addon undo doesn't put those back. Reinstall the Maddog for that.

Get it

The aircraft is a paid product of Leonardo, sold on flythemaddog.com. The test machine's copy was bought through the Contrail and simMarket route, and registration asks for the simMarket registration number. The installer is an Inno Setup program. Its name starts with Leonardo-Fly-the-Maddog-20th-Anniversary-Edition-FS24 and carries the build number.

Install it

Close the simulator and every other program of its prefix, and run nothing else while the installer works. The ground rules explain why. Then give the installer to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install maddog-md80 ~/Downloads/Leonardo-Fly-the-Maddog-20th-Anniversary-Edition-FS24-installer.exe

Use the name of the file you downloaded. Without a file name the command only prints where to get the program. With it, the command refuses to start while the simulator runs or any program is open in the prefix, and names those programs. Then it runs the installer alone in the simulator's prefix. On the test machine the Contrail store downloaded the installer and it ran in that prefix. The runner used there was not recorded.

At its end the installer opens the vendor's Maddog Manager. On the test machine that program exited with code 1. It is a WinUI 3 program, and WinUI 3 doesn't open on Wine (see "Known problems"). The install was complete: the Load Manager and MDClient were in the prefix, and the aircraft registered and flew afterwards.

Register it

The vendor's quick guide says to register in the Maddog Manager, which doesn't open. The Load Manager (Load Manager\maddog_lm.exe, a 32-bit Delphi program) has the same registration screen and does open. Close the simulator and every other program of the prefix, then:

~/flightsim-on-linux/bin/flightsim-on-linux addon launch maddog-md80 register

It refuses to start while the simulator or another program holds the prefix, and names what to close. Otherwise it opens the Load Manager alone in the prefix and waits until you close it. The key icon at the foot of its sidebar opens "Registration". It asks for your e-mail and the "Product Registration Number" from simMarket, and shows the machine's serial number (SN) and a Register button. The Load Manager writes the answer from Leonardo's server into registration.ini. This project never prints that file's key.

The SN comes from the serial of the C: volume that Wine reports, and the key carries that SN. By the vendor programs' code, a prefix recreated with another C: serial invalidates the key, and the reset on the same screen frees the activation so you can register again. Nobody has seen the serial change.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply maddog-md80

Close the simulator first. It makes one change in the prefix, only when .NET Framework 4.8 is there, and then runs the check: it sets mscoree to native under HKCU\Software\Wine\AppDefaults\MDClient.exe\DllOverrides, so that one program runs on Microsoft's .NET Framework 4.8 and not on wine-mono. Every other .NET program stays on wine-mono. If the key already holds another value, the command leaves it alone and says so.

The reason is cost. MDClient is the .NET Framework program the aircraft talks to while it flies. A timer in it ticks every 10 milliseconds. With the setting that closes MDClient together with the simulator on, each tick asks Windows for the simulator's process by name. On wine-mono that call keeps the wineserver, which the simulator shares, busy. Measured on the test machine on 22 October 2026, with the MD-80 loaded:

MDClient runs onContext switches a secondMDClient CPUWineserver CPU
wine-mono113,000 to 169,00041 to 47%40 to 44%
.NET Framework 4.83,722 to 4,04514 to 23%10 to 19%

With MDClient paused, the wineserver sat at 12%. With the simulator closed, MDClient on wine-mono cost 1% and the wineserver 2%, because the checks stop before the expensive call. The measurement shows which call costs, not why wine-mono makes it so slow.

How .NET Framework 4.8 reaches the prefix

The add-on doesn't carry its own copy of the .NET installer. The .NET Framework 4.8 add-on does this job, and the Maddog needs it first:

~/flightsim-on-linux/bin/flightsim-on-linux addon apply dotnet48

Close the simulator first. It downloads the .NET 4.8 and 4.0 installers from Microsoft, checks them against pinned hashes, installs 4.8 and Microsoft's mscoree.dll, and sets the registry values that go with them. Every other .NET program stays on wine-mono, which is told to ignore the Microsoft libraries now in the prefix. If you already ran addon apply fenix-a320 or addon apply dotnet48, .NET 4.8 is there and you can skip this. Run addon apply maddog-md80 afterwards.

The originals of the files it replaces go in compatdata/2537590/flightsim-on-linux-backup/dotnet48. addon undo dotnet48 puts them back. addon undo maddog-md80 doesn't, because other add-ons may need them.

Start it

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut maddog-md80

This writes two entries in your application menu, each with its program's icon when 7z and magick are installed: "Maddog Manager", the native Manager, and "Maddog registration", the same as addon launch maddog-md80 register above.

The native Manager

The vendor's Maddog Manager is a WinUI 3 program and doesn't open on Wine. You don't need it to fly. The native Manager does the same jobs directly on Linux. It is a Python program with a Qt 6 window, so it needs python-pyqt6 on Arch or python3-pyqt6 on Debian and Ubuntu. It has three pages:

  • Home. The installed version, whether Leonardo's site has a newer build, whether the aircraft is registered, the panel state that applies the next time the Maddog loads, and the Navigraph AIRAC cycle in the Maddog's work folder.
  • Liveries. The official liveries from flythemaddog.com, the ones in a local folder of zips, and the ones installed that are in neither. It installs and removes liveries and downloads the paint kit, with pause and resume. With the simulator open it refuses to install or remove, because the simulator reads the Maddog's package only when it starts.
  • Options. The same options as the vendor's Manager, from the simulator to the axis calibration. Each change is saved at once. Export and Import use the vendor's .mdc file.

Registration stays in the Load Manager. The Manager leaves out the avatars, which the vendor's Manager also hides in MSFS 2024, and it doesn't cover MSFS 2020. It finds the prefix and the Community folder from this project, or you can name the prefix with --prefix. Where the Load Manager's FSPath points at a folder that exists, the Manager uses that folder, because that is the folder the vendor's own programs use.

It writes the files the vendor's programs write: the livery folders and aircraft files in the Maddog package in Community, the package's layout.json and manifest.json, which it rebuilds after every install or removal the way the installer does, its maddogx.ini and maddogx.mdx, and the Maddog's own manager.ini and option files. What this page says about the vendor's Manager comes from its decompiled code. Nobody has seen it run here. By that code, the native Manager differs in four ways: it also rebuilds layout.json when you remove a livery, where the vendor's leaves the removed livery listed; Import writes the lights straight into maddogx.ini; it copies a panel state only when you choose one, where the vendor's copies it again every time it opens; and it reads a local zip's livery.cfg and thumbnail without unpacking the whole zip. On the test machine 17 liveries were installed with it.

MDClient

MDClient has to start with the simulator and run in the simulator's container. The plain way is exe.xml: the simulator starts MDClient itself. On 22 October 2026 MDClient ran that way on the test machine, on .NET Framework 4.8 once the override was set. If your exe.xml already starts MDClient, you have nothing more to do.

An exe.xml entry starts MDClient whatever aircraft you fly, and MDClient costs CPU all the while. The alternative is a service that starts it only when the Maddog is loaded. It reads the loaded aircraft from the simulator over SimConnect on a TCP port, so it needs the simconnect-tcp add-on first (addon apply simconnect-tcp). Then:

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher maddog-md80

This writes a user service called flightsim-on-linux-maddog-md80.service and switches it on. It looks at the simulator every 8 seconds. When the loaded aircraft's name contains "Maddog" (case ignored), it starts MDClient inside the simulator's container, and never a second copy. When another aircraft loads, it asks MDClient to end with a plain termination signal, and it never kills it. It does the same when the simulator closes, if it started that MDClient.

The watcher has not caught a real MD-80 yet. The journal of the test machine's own watcher, a script that predates this one, has no line for it opening MDClient, so this way has not been seen working with a real MD-80. exe.xml is the plain way. To start MDClient by hand with the simulator running:

~/flightsim-on-linux/bin/flightsim-on-linux addon launch maddog-md80 launch-mdclient

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check maddog-md80

It changes nothing, so you can run it with the simulator open. Each line starts with ok or FAIL:

  • the Maddog package is in Community;
  • the Load Manager's FSPath is the simulator's Community folder;
  • registration.ini holds a key and a purchase code. The check reads the file and prints only whether they are there;
  • the prefix has .NET Framework 4.8 and Microsoft's mscoree.dll;
  • mscoree is native for MDClient;
  • when the service file above exists, SimConnect listens on a TCP port above 1023.

Each FAIL says what to run.

Known problems

  • The vendor's Manager doesn't open. It is a WinUI 3 program. Use the native Manager above.
  • A new C: serial invalidates the key. See "Register it".
  • The EFB starts switched off. Hold its home button.
  • The Load Manager has a black background and white text. That is how the program looks. The screenshot in the vendor's Load Manager manual is the same.
  • The watcher has not caught a real MD-80. See "MDClient".

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo maddog-md80

Close the simulator first. It deletes the mscoree override for MDClient, so MDClient runs on wine-mono again. .NET Framework 4.8 stays in the prefix. The registration and the Maddog package are not touched, so what the native Manager wrote stays. Take out the menu entries and the service with:

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut maddog-md80 --remove
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher maddog-md80 --off
