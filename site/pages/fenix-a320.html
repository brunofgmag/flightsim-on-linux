title: Fenix A320 description: How to install and run the Fenix A320, A319 and A321 in MSFS 2024 under Proton: the Fenix Installer and its updates, the 1.0.353 installer that opens empty, packages that must not be links, .NET Framework 4.8 for the Fenix programs only, the geometry library and the DXVK the displays need, and how to undo it all. ---

Fenix A320, A319 and A321

The test machine has Fenix 3.0.0.7613 and Fenix Installer 1.0.359. The aircraft manifests there are dated 29 October 2026. It takes an installer, one command that sets up the prefix and one that proves it is set up. touches add-on files: it adds files to the Fenix deps folder and its displays folder, and puts back what was there when you undo it.

Get it

Download the Fenix Installer from fenixsim.com, after you sign in to your account. The download is a Velopack setup program with a WebView2 page. It installs the Fenix Installer, and the Fenix Installer installs and updates the aircraft. On the test machine the setup file was FenixInstaller-1.0.286-0763ce3.exe.

Install it

The Fenix needs Proton FS2024. Without it the aircraft won't power up, and the displays leak memory, lose frame rate within minutes and freeze. Pick Proton FS2024 for the simulator in Steam and start the simulator once with it. From Fenix Installer 1.0.353 the installer also needs a Proton FS2024 built with the installer fix (windows-storage-applicationdata-no-package.patch), or it can't open its package database and can't check the aircraft for updates. The check below tells you whether yours has it.

Close the simulator and every other program of its prefix, and run nothing else while the setup works. The ground rules explain why. Then give the setup file to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install fenix-a320 ~/Downloads/FenixInstaller-1.0.286-0763ce3.exe

Use the name of the file you downloaded. Without the file name the command only prints where to get the program. With it, the command refuses to start while the simulator runs or any program is open in the prefix, and names those programs. Then it runs the setup alone in the simulator's prefix, which puts the installer in AppData\Local\FenixApp. The setup opens the installer when it ends. Close that first window.

From then on open the installer with its own script, not by double-clicking the program:

~/flightsim-on-linux/bin/flightsim-on-linux addon launch fenix-a320 installer

It needs protontricks. It refuses to start while the simulator or any other program of the prefix is open, and names what to close. On the test machine, a Fenix Installer started while another program held the prefix crashed before its window appeared. Otherwise it opens the installer in its own window and keeps running until the installer and any update it applies have finished. Sign in, install the aircraft, then close the installer. On the test machine, with installer 1.0.355 and Proton FS2024, that window took mouse clicks and typing. Whether the 1.0.359 window does was not rechecked; its log shows three starts, on 22 and 24 October 2026, with no failure line.

Three things about the installer matter here:

  • It updates itself. On 21 October 2026 installer 1.0.286 downloaded the next version five seconds after it opened and didn't ask. The updater is Velopack: the installer runs Update.exe apply and quits. On Wine that update only finishes while the program that started the installer stays alive, and only when the installer was not started from inside its own current folder, because every Wine process keeps its current folder open and Velopack can't move it. The installer script waits for Update.exe and starts outside current. Started any other way, the update stops at "Checking application pre-requisites" and the old version comes back.
  • An update can delete linked packages. The installer updates the aircraft by replacing every file of its two packages, fnx-aircraft-320 and fnx-aircraft-319-321. On the test machine those two were Linux links made by a Community organiser. On 17 October 2026 an update through installer 1.0.286 left both links pointing at nothing, and the aircraft were gone from the simulator. The test machine saw the effect and not which call causes it. In a separate test with the same Proton, removing a folder that is a Linux link, through Windows calls, deleted the target folder and left the link dangling. Keep the Fenix packages as real folders in Community. After an update, this must print nothing: 
    find "$(~/flightsim-on-linux/bin/flightsim-on-linux machine --json | python3 -c 'import json, sys; print(json.load(sys.stdin)["community"])')" -maxdepth 1 -name 'fnx-*' -type l
    If it lists a link, delete the link with rm (not the folder behind it) and reinstall the aircraft in the installer, which then makes a real folder.
  • The packages must be plain folders for the same reason, so don't point a Community organiser at them.

If the installer window stays empty

On 21 October 2026 Fenix published Fenix Installer 1.0.353, rebuilt on .NET 10. It puts its page inside a Windows composition layer that Wine doesn't have, so under Wine the window stays empty. That page is also what checks for updates, so 1.0.353 never updates itself. Version 1.0.355, out a few hours later, went back to the kind of window Wine can show. The installer on the test machine updated itself from 1.0.355 to 1.0.359 without help. See which version you have:

cd "$(~/flightsim-on-linux/bin/flightsim-on-linux machine --json | python3 -c 'import json, sys; print(json.load(sys.stdin)["prefix"])')/drive_c/users/steamuser/AppData/Local/FenixApp"
grep -o '<version>[^<]*' current/sq.version

If it says 1.0.353, close the simulator and every other program of the prefix. Then, in the same folder, download 1.0.355 from the address the installer itself uses, check it and apply it:

curl -fL -o packages/FenixApp-1.0.355-1cf2ef7-full.nupkg https://software.fenixsim.com/FenixApp/FenixApp-1.0.355-1cf2ef7-full.nupkg
sha256sum packages/FenixApp-1.0.355-1cf2ef7-full.nupkg
protontricks --no-term -c 'wine "$PWD/Update.exe" apply --norestart --package "C:\users\steamuser\AppData\Local\FenixApp\packages\FenixApp-1.0.355-1cf2ef7-full.nupkg"' 2537590

sha256sum should print e4e9b327dca634e7ec7f6f4cf583bad824f60aa91f6b76cc6f1804b02094934f, and the update ends with Package version 1.0.355 applied successfully. Open the installer as above afterwards. It still needs the Proton FS2024 installer fix.

Make it run

The Fenix draws its displays either on the GPU, its default, or on the CPU. On the test machine both work. The setup below reads the mode from the Fenix settings file, which exists once you have loaded a Fenix aircraft in the simulator. If the check says fenixConfig.xml is missing, load one, quit and run the setup again. Close the simulator for the setup.

GPU mode needs a DXVK with three fixes in the Fenix deps folder: the adapter of a shared texture, a keyed mutex that waits for what the other process drew, and a wait that gives up when its timeout runs out. Build it once. It takes about two minutes and needs meson, ninja, glslang and the MinGW-w64 cross compiler:

~/flightsim-on-linux/bin/flightsim-on-linux dxvk build

It downloads DXVK, applies the fixes, compiles d3d11.dll and dxgi.dll, tests them in a throwaway prefix and keeps them in ~/.cache/flightsim-on-linux/dxvk-fenix. If a test fails, or can't run on your machine, nothing is kept.

CPU mode needs no DXVK. In the Fenix settings, tick USE DISPLAY SAFE MODE and FORCE SAFE MODE CPU RENDERING and apply. The fenix-a320-linux-patch project, which drew its displays on the CPU, says the weather radar doesn't work that way.

~/flightsim-on-linux/bin/flightsim-on-linux addon apply fenix-a320

It does four things, skips any that are already done, and then runs the check below:

  1. It puts .NET Framework 4.8 in the prefix and uses it for the Fenix programs only. The Fenix runner, the bootstrapper and the system, CDU and display programs need Microsoft's .NET. On Wine's own .NET replacement, wine-mono, they spin or quit within half a second. The first half is the .NET Framework 4.8 add-on, which this command runs for you: it downloads the .NET 4.8 and 4.0 installers from Microsoft, checks them against pinned hashes, installs 4.8 and Microsoft's mscoree.dll, and tells wine-mono to ignore the Microsoft libraries now in the prefix. Without that, Lorby AAO crashed when it started. The second half is this add-on's own: it tells Wine to use Microsoft's .NET for those five programs only, and every other .NET program in the prefix stays on wine-mono.
  2. It builds the geometry library. Wine's Direct2D ignores line joins, so the route line escapes the navigation display. Proton FS2024 borrows only the geometry from Microsoft's own Direct2D, in the display program only. The command downloads the Windows 7 update that holds it and Microsoft's patching library, rebuilds d2d1_geometry.dll with a small helper from the fenix-a320-linux-patch project, checks every step against a known hash and puts the result in system32. Microsoft's files are never part of this repository.
  3. It puts the DXVK in place. In GPU mode it copies the DXVK you built into deps, and into deps/displays, where Fenix 3 keeps its display program. Without it there, the Fenix 3 displays stay dark. In CPU mode it copies nothing, and puts back the files it replaced if you used GPU mode before. With two GPUs, it also adds a line naming the dedicated one to dxvk.conf in both folders. The display program creates Direct3D devices even in CPU mode, and on the test machine DXVK picked the integrated GPU and the displays stayed dark. With one GPU it adds no filter.
  4. It makes sure the simulator starts the Fenix. The simulator opens the Fenix bootstrapper from exe.xml, and the bootstrapper refuses to run any other way. The Fenix installer writes that entry. The command adds it only if it is missing, and leaves every other line of the file as it was.

Before changing anything it keeps a copy of what was there in compatdata/2537590/flightsim-on-linux-backup/fenix-a320. The Windows version of the prefix comes out the same as it went in.

Start it

The simulator starts the Fenix by itself, through the exe.xml entry above. Only the installer needs a way to open:

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut fenix-a320

This writes an entry called "Fenix Installer" in your application menu, with the installer's own icon when 7z and magick are installed. It runs the same installer script, so it refuses with a desktop notice, and says why, when the simulator or another program holds the prefix. Remove it with addon shortcut fenix-a320 --remove.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check fenix-a320

It prints one line per thing it looked at, each starting with ok or FAIL, and every FAIL says what to run. It changes nothing, so you can run it with the simulator open. Fenix 3 needs a Proton FS2024 built on 21 October 2026 or later: with an older build, the runner quits as soon as it starts and the cockpit stays dark, and the check names the fixes your build lacks. A Fenix update can replace the files in deps. Run the check after one. The last line looks at Community: it says ok when no package named fnx-* there is a Linux link, and otherwise fails with one line for each link: on the test machine an update left two linked packages pointing at nothing. It is the same look as the find command above.

Known problems

If the displays don't come up

With the video card almost full, the cockpit displays may not start. On Windows the NVIDIA driver moves the excess to system memory; on Linux it refuses to create anything new, and the Fenix display program can't get its Direct3D device. On the test machine this happened at a busy airport on 17 October 2026, with 15,876 of the RTX 4080's 16,376 MiB in use: the display program quit three times while creating its device, in CPU mode as well. At a quiet airport, with about 2.4 GB free, the displays started. In the Fenix runner window, press RESTART DISPLAY under System Status and the displays come back. The optional setting below makes them use less video memory.

Optional: less video memory for the displays

This isn't needed to fly, and it only helped because the test machine ran short of video memory in 4K. In CPU mode with <multithread>true</multithread>, the display program created 13 Direct3D devices and used 622 MiB of the RTX 4080. With false it created 2 and used 208 MiB, and the displays didn't look any slower. No setting in the Fenix window was found for it. With the simulator closed, edit the value in C:\ProgramData\Fenix\FenixSim A320\fenixConfig.xml inside the prefix. Keep a copy of the file first.

If the aircraft has no systems after loading

Rarely, the Fenix runner quits a few seconds after it opens. On the test machine it happened once in 24 starts between 17 and 18 October 2026, and once before that, on 16 October, under gamescope with the X11 driver, so it isn't tied to Wine's Wayland driver. The bootstrapper keeps running without it, and the aircraft has no systems. The Fenix crash log shows an "invalid handle" error (0xc0000008) as the runner starts. Go back to the simulator's main menu and start the flight again in a Fenix. The bootstrapper then opens the runner again, without restarting the simulator. The cause hasn't been proven. It looks like a race inside the Fenix itself, and nothing in the Linux setup has been found to fix it.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo fenix-a320

It removes the bootstrapper entry if the command added it, puts back the deps files and system32 files it replaced, and stops the Fenix programs from using Microsoft's .NET. .NET 4.8 stays installed, with Microsoft's mscoree.dll, and wine-mono keeps ignoring the Microsoft libraries: with 4.8 in the prefix, letting wine-mono load them makes other add-ons crash, and other add-ons use that mscoree.dll. addon undo dotnet48 gives the original mscoree.dll back. The menu entry is removed with addon shortcut fenix-a320 --remove.
