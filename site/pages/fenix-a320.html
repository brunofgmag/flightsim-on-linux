title: Fenix A320 description: How to run the Fenix A320, A319 and A321 in MSFS 2024 under Proton: the Fenix Installer and its updates, .NET Framework 4.8 for the Fenix programs only, the geometry library and the DXVK the displays need, and how to undo it all. ---

Fenix A320, A319 and A321

Tested with Fenix 2.4.1.0 on 18 October 2026. One command sets up the prefix for the Fenix, and another proves it is set up. touches add-on files: it adds files to the Fenix deps folder and puts back what was there when you undo it.

Before you start

The Fenix needs Proton FS2024. Without it the aircraft won't power up, and the displays leak memory, lose frame rate within minutes and freeze. Pick Proton FS2024 for the simulator in Steam, and start the simulator once with it before you go on.

Close the simulator for every step on this page except the check and the last section.

Install the Fenix

Download the Fenix Installer from fenixsim.com and run its setup once in the simulator's prefix:

protontricks-launch --no-term --appid 2537590 ~/Downloads/FenixInstaller-Setup.exe

Use the name of the file you downloaded. The setup installs the installer and opens it. Close that first window, and from then on open the installer with:

~/flightsim-on-linux/addons/fenix-a320/installer

It needs protontricks. It refuses to start while the simulator or any other program of the prefix is open, and names what to close. On the test machine, a Fenix Installer started while another program held the prefix crashed before its window appeared. Otherwise it opens the installer in its own window and keeps running until the installer and any update it applies have finished. On the test machine, with installer 1.0.355 and Proton FS2024, that window took mouse clicks and typing. Sign in, install the aircraft, then close the installer. From version 1.0.353 the installer also needs a Proton FS2024 built with the installer fix, and the check below tells you whether yours has it. Without it, the installer can't open its package database or check the aircraft for updates.

If the installer window stays empty

On 2026-10-21 Fenix published Fenix Installer 1.0.353, rebuilt on .NET 10. It puts its page inside a Windows composition layer that Wine doesn't have, so under Wine the window stays empty. That page is also what checks for updates, so 1.0.353 never updates itself. Version 1.0.355, out a few hours later, went back to the kind of window Wine can show. See which version you have:

cd "$(~/flightsim-on-linux/bin/flightsim-on-linux machine --json | python3 -c 'import json, sys; print(json.load(sys.stdin)["prefix"])')/drive_c/users/steamuser/AppData/Local/FenixApp"
grep -o '<version>[^<]*' current/sq.version

If it says 1.0.353, close the simulator and every other program of the prefix. Then, in the same folder, download 1.0.355 from the address the installer itself uses, check it and apply it:

curl -fL -o packages/FenixApp-1.0.355-1cf2ef7-full.nupkg https://software.fenixsim.com/FenixApp/FenixApp-1.0.355-1cf2ef7-full.nupkg
sha256sum packages/FenixApp-1.0.355-1cf2ef7-full.nupkg
protontricks --no-term -c 'wine "$PWD/Update.exe" apply --norestart --package "C:\users\steamuser\AppData\Local\FenixApp\packages\FenixApp-1.0.355-1cf2ef7-full.nupkg"' 2537590

sha256sum should print e4e9b327dca634e7ec7f6f4cf583bad824f60aa91f6b76cc6f1804b02094934f, and the update ends with Package version 1.0.355 applied successfully. Open the installer as above afterwards. It also needs a Proton FS2024 built with the installer fix, or it can't open its package database.

Choose how the displays draw

The Fenix draws its displays either on the GPU, its default, or on the CPU. On the test machine both work. The setup below reads the mode from the Fenix settings file, which exists once you have loaded a Fenix aircraft in the simulator. If the check says fenixConfig.xml is missing, load one, quit and run the setup again.

GPU mode needs a DXVK with three fixes in the Fenix deps folder: the adapter of a shared texture, a keyed mutex that waits for what the other process drew, and a wait that gives up when its timeout runs out. Build it once. It takes about two minutes and needs meson, ninja, glslang and the MinGW-w64 cross compiler:

~/flightsim-on-linux/bin/flightsim-on-linux dxvk build

It downloads DXVK, applies the fixes, compiles d3d11.dll and dxgi.dll, tests them in a throwaway prefix and keeps them in ~/.cache/flightsim-on-linux/dxvk-fenix. If a test fails, or can't run on your machine, nothing is kept.

CPU mode needs no DXVK. In the Fenix settings, tick USE DISPLAY SAFE MODE and FORCE SAFE MODE CPU RENDERING and apply. The fenix-a320-linux-patch project, which drew its displays on the CPU, says the weather radar doesn't work that way.

Set up the prefix

~/flightsim-on-linux/bin/flightsim-on-linux addon apply fenix-a320

It does four things, skips any that are already done, and then runs the check below:

  1. It installs .NET Framework 4.8 for the Fenix programs only. The Fenix runner, the bootstrapper and the system, CDU and display programs need Microsoft's .NET. On Wine's own .NET replacement, wine-mono, they spin or quit within half a second. The command downloads the .NET 4.8 and 4.0 installers from Microsoft, checks them against pinned hashes, installs 4.8 and Microsoft's mscoree.dll, and tells Wine to use them for those five programs only. Every other .NET program in the prefix stays on wine-mono, which is also told to ignore the Microsoft libraries now in the prefix. Without that, Lorby AAO crashed when it started.
  2. It builds the geometry library. Wine's Direct2D ignores line joins, so the route line escapes the navigation display. Proton FS2024 borrows only the geometry from Microsoft's own Direct2D, in the display program only. The command downloads the Windows 7 update that holds it and Microsoft's patching library, rebuilds d2d1_geometry.dll with a small helper from the fenix-a320-linux-patch project, checks every step against a known hash and puts the result in system32. Microsoft's files are never part of this repository.
  3. It puts the DXVK in place. In GPU mode it copies the DXVK you built into deps. In CPU mode it copies nothing, and puts back the files it replaced if you used GPU mode before. With two GPUs, it also adds a line to deps/dxvk.conf naming the dedicated one. The display program creates Direct3D devices even in CPU mode, and on the test machine DXVK picked the integrated GPU and the displays stayed dark. With one GPU it adds no filter.
  4. It makes sure the simulator starts the Fenix. The simulator opens the Fenix bootstrapper from exe.xml, and the bootstrapper refuses to run any other way. The Fenix installer writes that entry. The command adds it only if it is missing, and leaves every other line of the file as it was.

Before changing anything it keeps a copy of what was there in compatdata/2537590/flightsim-on-linux-backup/fenix-a320. The Windows version of the prefix comes out the same as it went in.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check fenix-a320

It prints one line per thing it looked at, each starting with ok or FAIL, and every FAIL says what to run. It changes nothing, so you can run it with the simulator open. A Fenix update can replace the files in deps. Run the check after one.

Undo it

~/flightsim-on-linux/bin/flightsim-on-linux addon undo fenix-a320

It removes the bootstrapper entry if the command added it, puts back the deps files and system32 files it replaced, and stops the Fenix programs from using Microsoft's .NET. .NET 4.8 stays installed, and wine-mono keeps ignoring the Microsoft libraries: with 4.8 in the prefix, letting wine-mono load them makes other add-ons crash.

If the displays don't come up

With the video card almost full, the cockpit displays may not start. On Windows the NVIDIA driver moves the excess to system memory; on Linux it refuses to create anything new, and the Fenix display program can't get its Direct3D device. On the test machine this happened at a busy airport on 17 October 2026, with 15,876 of the RTX 4080's 16,376 MiB in use: the display program quit three times while creating its device, in CPU mode as well. At a quiet airport, with about 2.4 GB free, the displays started. In the Fenix runner window, press RESTART DISPLAY under System Status and the displays come back. The optional setting below makes them use less video memory.

Optional: less video memory for the displays

This isn't needed to fly, and it only helped because the test machine ran short of video memory in 4K. In CPU mode with <multithread>true</multithread>, the display program created 13 Direct3D devices and used 622 MiB of the RTX 4080. With false it created 2 and used 208 MiB, and the displays didn't look any slower. No setting in the Fenix window was found for it. With the simulator closed, edit the value in C:\ProgramData\Fenix\FenixSim A320\fenixConfig.xml inside the prefix. Keep a copy of the file first.

If the aircraft has no systems after loading

Rarely, the Fenix runner quits a few seconds after it opens. On the test machine it happened once in 24 starts between 17 and 18 October 2026, and once before that, on 16 October, under gamescope with the X11 driver, so it isn't tied to Wine's Wayland driver. The bootstrapper keeps running without it, and the aircraft has no systems. The Fenix crash log shows an "invalid handle" error (0xc0000008) as the runner starts. Go back to the simulator's main menu and start the flight again in a Fenix. The bootstrapper then opens the runner again, without restarting the simulator. The cause hasn't been proven. It looks like a race inside the Fenix itself, and nothing in the Linux setup has been found to fix it.
