title: ChasePlane description: How to install and run ChasePlane in MSFS 2024 under Proton: the installer that needs an empty prefix, the two stand-ins for Windows components, the Steam launch option, the bridge service, and the Proton FS2024 patches that keep the camera drag and the frame rate right. ---

ChasePlane

Tested with ChasePlane 2026.39.1.16 on 17 October 2026. It runs after two small stand-ins for Windows components are in the prefix, one launch option is set in Steam, and the bridge is started with the host's Wine, attached to the simulator's Wine server. The camera drag and a stutter need Proton FS2024.

Get it

ChasePlane is made by Parallel 42. Where to buy it isn't recorded here. The installer on the test machine was ChasePlane - Experimental.exe, version 2026.39.1.16, a real .NET 8 installer (it doesn't run on wine-mono). It installs the package p42-util-chaseplane (26.39.1) into Community, together with the manager ChasePlane for MSFS2024.exe and the bridge CP MSFS Bridge.exe, and it writes the entries for them in exe.xml.

Install it

The prefix has to be empty: close the simulator and every other program, and run nothing else while the installer works. The ground rules explain why. On 13 October 2026 the installer ended with "Installation failed" and an access denied message, error 5 from EnumProcessModulesEx, while PMDG Operations Center 3 was open in the same prefix. With nothing else open it installed on the first try. Then give the installer to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install chaseplane ~/Downloads/"ChasePlane - Experimental.exe"

It refuses to start while the simulator runs or any program is open in the prefix, and names those programs. It runs the installer in the simulator's prefix with Proton's Wine. Nothing else is needed for the installer: no patch, no override.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply chaseplane

Close the simulator and the manager first. The command builds two small programs on your machine, copies them into the prefix, registers them, and prints the one step that is yours. Building needs the .NET SDK for the first one (dotnet-sdk on Arch, dotnet-sdk-8.0 on Debian and Ubuntu); without it, the build falls back to the compiler in Proton's wine-mono, run through Wine in your prefix. The second one needs x86_64-w64-mingw32-gcc (mingw-w64-gcc on Arch, gcc-mingw-w64-x86-64 on Debian and Ubuntu).

  • A stand-in for the CAppResolver class. ChasePlane's libraries ask Windows, through the COM class CAppResolver, for the application id of their process. Wine doesn't have the class, and the program stops in the constructor of its window with "class not registered". AppResolverShim.dll, a small managed COM server, answers with the name of the process. It goes to C:\appresolver and is registered under that class. On 1 November 2026, in a disposable prefix on the test machine, a small client that asked the registered class for the id of its own process got the process name back, with the DLL built by the .NET SDK and with the one built by wine-mono's compiler. Without the registration the same client got "class not registered".
  • A stand-in for the WinRT ToastNotificationManager. After the first one, the same libraries ask for the WinRT class Windows.UI.Notifications.ToastNotificationManager to create their notifier, and Wine doesn't implement that either. toaststub.dll answers with a notifier that does nothing. It goes to the same folder, with its own registry entry.
  • httpapi off for the bridge. The bridge starts its web socket server on port 8652 through Wine's http.sys, and Wine has the HTTP server without the web socket part. The first connection of the panel dies with The type initializer for 'System.Net.WebSockets.WebSocketProtocolComponent' threw an exception. Turning httpapi off for CP MSFS Bridge.exe alone, in HKCU\Software\Wine\AppDefaults\CP MSFS Bridge.exe\DllOverrides, makes the server fail the way it used to and fall back to its own plain TCP one; the log then says WS: Raw TCP fallback activated, port 8651 answers 200 and 8652 completes the handshake. The registry entry covers the bridge however it starts, including when the simulator starts it. The launch script also turns it off.
  • The Steam launch option. apply doesn't edit Steam's files. It prints the line to add, with the value worked out for your machine: 
    STEAM_COMPAT_LIBRARY_PATHS=/path/to/your/steam/library
    In Steam, open the properties of Microsoft Flight Simulator 2024 and put that before %command% in the launch options, keeping what is already there. The path is the Steam library that holds the simulator, the folder that has steamapps inside; bin/flightsim-on-linux machine --json prints it as sim_library. Without the option, Proton maps drive S: to the steamapps folder itself, the path of the simulator has no steamapps\common in it, and the bridge doesn't recognise the installation ("Unknown version") and quits. Start the simulator once afterwards so Proton maps drive S: again.

Proton FS2024 carries six patches that ChasePlane needs. Each is in the check:

  • server-process-vm-eperm-per-call.patch, the stutter. When the fast way of reading another process's memory fails once with EPERM, stock Wine switches it off for every process and from then on every read stops the target's main thread with ptrace. ChasePlane reads the simulator's camera all the time, and the simulator's main thread stood still for up to 300 ms of every second. The patch falls back to ptrace for that one call only.
  • The camera drag arrow. During a drag the simulator hides the cursor and clips it to one pixel for 29 ms, releases it for 1 ms, and repeats. Five patches to the Wayland driver make the arrow behave:
    • winewayland-hidden-cursor-window-clip-confines.patch: when the cursor is hidden and the clip covers the whole window, the pointer is confined instead of locked. A locked pointer drops absolute motion, and the arrow froze until the window lost focus.
    • winewayland-commit-pointer-constraint-changes.patch: the surface is committed after every lock or confinement the clip makes or releases. KWin 6.8 applies those changes only at the next commit, and the simulator's main surface almost never commits.
    • winewayland-small-clip-warps-pointer-inside.patch: when the clip is smaller than the window, the pointer is first moved to the nearest point of the clip, as Windows does. A confinement only holds while the pointer is already inside it, and once it drifted one pixel in a released millisecond, the arrow wandered off the screen.
    • winewayland-clip-at-least-one-pixel.patch: a confinement never gets an empty region. At 125% scale a one-pixel clip turned into an empty region, and one drag sent 849 of them.
    • winewayland-warp-before-confining.patch: the warp comes before the confinement and a new confinement replaces the old one. KWin 6.7 decides whether a confinement holds only when it is created, and only if the pointer is inside at that moment. In an isolated KWin 6.7.5 only 2 of 97 one-pixel confinements held before this patch, and the arrow shook in place.

Under the Wayland driver only. What these patches do in the simulator in flight isn't recorded beyond the numbers above.

Start it

The installer writes entries for the manager and the bridge in exe.xml, so the simulator opens the manager by itself. The bridge entry doesn't leave a bridge standing: started from inside the simulator's container with nsenter, which is what flightsim-on-linux run does and what an exe.xml entry amounts to, it exited in 0.2 seconds with code 0 and no log, in more than 30 tries on 14 October 2026. The bridge does start when the simulator opens it itself through chaseplanemsfs24://, but that path doesn't pass httpapi=d, which is why the registry entry above exists.

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher chaseplane
~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut chaseplane

The first writes a user service, flightsim-on-linux-chaseplane.service, and switches it on. It looks every 8 seconds. About 20 seconds after a new simulator appears, and only when nothing listens on port 8651, it runs launch-bridge, which starts the bridge with Proton's own Wine on the host, in the simulator's prefix, with httpapi=d and chaseplanemsfs24:// as its argument. It copies the prefix, the synchronisation mode (WINEESYNC, WINEFSYNC, PROTON_NO_NTSYNC), the display (WAYLAND_DISPLAY, DISPLAY, XAUTHORITY) and the DLL path and overrides from the running simulator's process with bin/flightsim-on-linux sim-env, so nothing about your session is written in the script. On 17 October 2026 the old service pinned wayland-0 while the only socket was wayland-1, and the bridge died four times with a Win32Exception in the constructor of its window. The bridge gets the Wine display driver the simulator has, found from PROTON_ENABLE_WAYLAND in the same process: Wayland when it is 1, X11 otherwise. The old private service forced the same driver because a bridge on the other one failed in the constructor of its window; that was not measured again here. When the simulator closes it sends the bridge SIGTERM. That matters: a bridge left behind keeps Steam counting the game as running. Shortcuts and watchers has the rest.

The second writes a menu entry called "ChasePlane" that opens the manager. With the simulator closed it runs wine <manager>; wineserver -w through protontricks -c, the way the Flow manager has to open: a Parallel 42 manager can hand over to a copy of itself in a temporary folder and exit, and a bare protontricks-launch would kill the copy when the first process returns. With the simulator open it starts the manager in the simulator's container.

The bridge starts with the host's Wine and not with the container's. On 14 October 2026 the only bridge that stayed up was the one a service of the test machine started with the host's Wine, attached to the simulator's Wine server; on 17 October 2026 a bridge started that way again connected to SimConnect, opened ports 8651 and 8652 and stayed up. In the container the bridge ran five queries for the modules of its own process, which succeeded, loaded System.Diagnostics.TraceSource and left. With the host's Wine those queries fail with error 5. The reading is that the bridge decides to quit when it can read its own path; that was not confirmed, and a new bridge build can change it. launch-bridge follows the route that stayed up. It was tested here with a stand-in for Wine and a stand-in for the simulator's process folder, and has not been run against the simulator since it was written, so if the panel stays on "loading" and nothing listens on 8651, look at ~/.cache/flightsim-on-linux/logs/chaseplane-bridge.log first.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check chaseplane

It prints eleven lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • AppResolverShim.dll is in C:\appresolver and registered for the CAppResolver class;
  • toaststub.dll is there and registered for the ToastNotificationManager class;
  • httpapi is off for CP MSFS Bridge.exe;
  • the launch options saved in Steam for the simulator hold STEAM_COMPAT_LIBRARY_PATHS with your library;
  • drive S: of the prefix is the library itself;
  • the six Proton patches above are in your Proton build, and its files are the ones the build recorded.

When the Proton lines fail, rebuild with bin/flightsim-on-linux proton build.

Known problems

  • The ChasePlane Bridge entry that the installer puts in exe.xml leaves no bridge standing, as above.
  • The panel stays on "loading" for ever with no error when a bridge ran once without httpapi off: a leftover winedevice.exe hosting http.sys holds the connections the simulator had opened to port 8652. ss -tnp state established '( sport = :8652 )' shows who holds each connection. Ending that winedevice.exe frees them, and on 17 October 2026 the Overlay and the Toolbar reconnected within 20 seconds.
  • The first start after an install patches files of the simulator and asks you to restart it. It happens once for each ChasePlane build.
  • WS: Raw TCP fallback activated in the bridge log is the intended state.
  • The two stand-ins date from July. They were not measured again with each ChasePlane build, and a new build can ask Windows for something else.
  • The installers don't need a virtual desktop: the October installers opened without one.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher chaseplane --off
~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut chaseplane --remove
~/flightsim-on-linux/bin/flightsim-on-linux addon undo chaseplane

The first two take out the service and the menu entry. undo removes the httpapi override of the bridge, and removes the two stand-ins and their registry entries unless Flow still uses them, in which case they stay until you undo that too. A stand-in that was already in C:\appresolver before the fix is put back. It doesn't touch your Steam launch options: remove STEAM_COMPAT_LIBRARY_PATHS there yourself if you want it gone.
