AtmosphereMod

Tested with AtmosphereMod 0.5.1 on 1 November 2026, with 0.7.1 on 9 November 2026 and with 0.7.2 on 12 November 2026. It is a ReShade add-on that replaces the simulator's haze, sky colours and cloud lighting, and takes its weather from METARs. It needs ReShade 6.8 or newer. The mod's own installer does the work, run under Wine in the add-ons prefix. Nothing of the mod is changed or kept in this repository.

Get it

AtmosphereMod is free, from the project's releases page on GitHub. The file is AtmosphereMod-0.7.2.zip of release 0.7.2. You don't need to download it yourself: the install command does.

The licence is the AtmosphereMod Freeware Licence, in the zip as LICENSE. It lets you download, install and use the mod for yourself, and change its tunables.ini. It does not let anyone redistribute it in any form (section 2a) or share the shaders its installer makes from your simulator's files (2f and 3). So this repository ships no file of the mod, and no modified copy of one. The command downloads the official asset, checks its hash and runs it.

The author says it is experimental and was tested on one PC, and that you use it at your own risk. The installer prints that disclaimer and asks for a yes. The command answers yes for you, so read the README in the zip first if you haven't.

Install it

Install ReShade first. The simulator has to be closed. The command doesn't need the rest of the simulator's prefix to be free, because the installer runs in the add-ons prefix.

~/flightsim-on-linux/bin/flightsim-on-linux addon install atmospheremod

The command downloads https://github.com/tomwhoca/AtmosphereMod/releases/download/v0.7.2/AtmosphereMod-0.7.2.zip with curl, checks that its sha256 is 6d916cab5c7331708911b63286547452991ed0456d70883d7ef249efa937a118, the digest GitHub lists for that asset, and keeps it in ~/.cache/flightsim-on-linux/downloads. A file with another hash is thrown away and nothing runs. The hash is pinned because this is the release that was tested. A newer release needs a newer test.

If you already have the zip, give it to the command: addon install atmospheremod /path/to/AtmosphereMod-0.7.2.zip. It must be the same release.

It refuses while the simulator runs, and when the simulator's folder has no ReShade dxgi.dll. If the add-ons prefix doesn't exist yet, it makes it first, and that needs the simulator and every program of its prefix closed. Then it unpacks the zip into a temporary folder, runs the zip's own Python, installer\python\python.exe, on installer\install.py with Proton's Wine in the add-ons prefix, and deletes the folder. The arguments are the mod's own:

  • --data C:\users\steamuser\AppData\Local\AtmosphereMod, which is drive_c/users/steamuser/AppData/Local/AtmosphereMod in the simulator's prefix;
  • --yes;
  • --sim and --community, the simulator's folder and the Community folder, as Z: paths;
  • --dxc, the folder with the DirectX Shader Compiler that comes in the zip;
  • --renodx, only when a renodx-*.addon64 is in the simulator's folder. The command prints a line when it adds it. It moves AtmosphereMod's parameters to register space 51, out of the way of the RenoDX HDR mod. Without it, the installer keeps the space it finds in ReShade.ini, and 50 when there is none.

The installer then does what it does on Windows. It extracts the simulator's shaders from the shader pack in the simulator's own Shaders folder, SHADERSPAK.<hash>.SM6.PC.PAK, and patches them in the data folder. On the test machine release 0.5.1 patched 258 shaders, and 0.7.1 and 0.7.2 patched 3079 each, from the shader pack SHADERSPAK.d5d2118d.SM6.PC.PAK, and none refused any. It copies AtmosphereMod.addon64 into the simulator's folder, puts the EFB app atmospheremod-weather in Community, and writes an [ATMOSPHEREMOD] section into ReShade.ini with DataPath, TunablesPath, InjectRootSignature=1, InjectGraphicsRootSignature=1 and, since 0.7.0, RegisterSpace. The first time, it keeps the original ReShade.ini beside it as ReShade.ini.atmospheremod.bak. Running it again keeps your tunables.ini and adds the settings that are new. That held when 0.7.1 went over 0.7.0 on 9 November 2026, and when 0.7.2 went over 0.7.1 on 12 November 2026.

The simulator's shader pack is not changed: the add-on swaps the shaders in memory.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply atmospheremod

This changes nothing, and then runs the check. The installer already did everything, and there is no launch option: ReShade loads the add-on from the simulator's folder.

Three things differ from Windows in how the installer is called. Each one is a trap that was hit on 1 November 2026 with release 0.5.1. The code of release 0.7.2 still has all three, and the command avoids them: its install.py is the same as in 0.7.1.

  • The signature check. The installer checks that dxc.exe, dxcompiler.dll and dxil.dll carry Microsoft's signature by calling PowerShell. Wine's PowerShell is a stub that exits 0 and prints nothing, so the check fails, the installer drops the compiler that came in the zip and tries to download another, which would fail the same way. Passing --dxc makes it use the zip's copy: the installer tries the folder it is given first, without the signature check. The check was done outside Wine on that day: the Authenticode digest of each of the three files was inside its signature, issued to Microsoft Corporation. The certificate chain was not validated. The three files and installer\python\python.exe are byte for byte the same in the zips of 0.5.1, 0.7.0, 0.7.1 and 0.7.2.
  • The simulator check. The installer asks tasklist whether the simulator runs. In the add-ons prefix, tasklist sees only the FlightSimulator2024.exe of the sentinel, so it can't tell. The command looks at the simulator itself and refuses to go on while it runs.
  • The EFB app and a link in Community. The installer replaces the folder Community/atmospheremod-weather with shutil.rmtree and a copy. Under Wine a Linux link looks like a plain folder: the mod's Python 3.14.9 answered is_symlink() false for a link, and rmtree deleted the folder the link pointed to and left the link dangling. If atmospheremod-weather in Community is a link, the command passes the folder that holds the real app as --community, so the installer replaces the real folder and the link keeps working. If it is a real folder, which is how the installer puts it, the command passes Community itself. Release 0.7.1 removes a link in Community as a link when it uninstalls, but that was not tried under Wine, and the install still replaces the folder with rmtree.

The proof on the test machine: ReShade 6.8.0.2155 registered release 0.5.1 in ReShade.log at the first start after the install, and the log counted 254 shader replacements and no error. On 9 November 2026 it registered 0.7.1.0, and four minutes after the simulator started the log had 732 replacements. That day the 0.7.0 and 0.7.1 installers ran with the arguments above from a script on the test machine. This command itself was not run with 0.7.1. Its check was: against that install it printed eight ok lines, with 3079 shaders patched and 3079 .cso files in the shaders folder, and register space 51 in both install.json and ReShade.ini. On 12 November 2026 the 0.7.2 installer ran over 0.7.1 from the same script, without --renodx, and kept space 51. At the next start ReShade registered 0.7.2.0, and the log had 734 replacements and no error.

Start it

There is nothing to start. The add-on loads with the simulator. Per the mod's README, Ctrl+Shift+F9 switches between the mod and the stock shaders, Ctrl+Shift+F10 reloads tunables.ini, and the settings are also in the AtmosphereMod app on the EFB tablet. Release 0.7.1 adds a performance report at the end of the app's page. It measures the mod's cost for about 36 seconds and sends the result to the author only when you tap Send. It was not tried on the test machine.

The weather comes from the EFB app, which passes the METARs to the add-on. On the test machine the first METAR arrived at SBFZ, where the flight started, and 14 minutes later the add-on had anchored SBFZ and SBMS. The add-on talks to SimConnect by the pipe, so it needs no SimConnect over TCP: ss -tnp showed no socket of the simulator on port 5111, the port in SimConnect.xml.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check atmospheremod

It prints six lines, each starting with ok or FAIL, and it changes nothing. A release from 0.7.0 on adds a line about the register space, and a log to read adds one more. The six are:

  • ReShade's dxgi.dll and AtmosphereMod.addon64 are in the simulator's folder (two lines);
  • [ATMOSPHEREMOD] in ReShade.ini has DataPath and TunablesPath;
  • install.json in the data folder says no shader failed to patch, and the number it says were patched is the number of .cso files in the shaders folder (two lines);
  • the pak in install.json is the shader pack in the simulator's Shaders folder now. If it isn't, the simulator was updated, and the line says to run the install again;
  • from 0.7.0 on, the register_space in install.json, the space the shaders were patched for, is the space RegisterSpace under [ATMOSPHEREMOD] gives the add-on, where no RegisterSpace means 50. AtmosphereMod's README says the two must match, or the simulator keeps its own shaders. When they differ, the line says to run the install again, which patches the shaders for the space in ReShade.ini, or for 51 when RenoDX is in the folder;
  • when ReShade.log is newer than the install, it says ReShade registered AtmosphereMod. A log from before the install says nothing either way, and a newer one without the registration fails.

Known problems

  • Run the install again after every simulator update. The patched shaders come from the shader pack that was there at the install, and a new pack makes the patches stale. The check catches it: the line about the shader pack fails and says the simulator was updated. Nothing runs the install for you.
  • The RenoDX HDR mod and AtmosphereMod clash when AtmosphereMod's parameters are in register space 50, as they are without --renodx. RenoDX then fails to replace its shaders and the image doesn't change. Install RenoDX first and AtmosphereMod after it, so the install command adds --renodx. That guide has the cause.
  • The Proton on the test machine carries the two vkd3d-proton patches of the Glass Cockpit DLSS Fix. AtmosphereMod was not tried without them.
  • The cost in frame rate was not measured, and Ctrl+Shift+F9 was not tried on the test machine.
  • If the picture looks wrong, Ctrl+Shift+F9 puts the stock shaders back at once.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon undo atmospheremod

The simulator has to be closed. The command runs the installer's own --uninstall the same way, with the same Community folder, and answers yes to "Uninstall AtmosphereMod?" and no to deleting the data folder. It removes AtmosphereMod.addon64, the [ATMOSPHEREMOD] section of ReShade.ini and the EFB app. It uses the zip in the cache, or downloads it again with the same hash check. When none of those three is there, it says AtmosphereMod isn't installed and stops.

These stay: ReShade.ini.atmospheremod.bak in the simulator's folder, and the data folder with the patched shaders, the logs and your tunables.ini. Delete the data folder yourself to remove them. A later install picks up your tunables.ini.

undo was not run on the test machine's own simulator folder. It ran against a fake simulator folder in a throwaway add-ons prefix on 5 November 2026, with the zip's own installer, and removed the three things above and kept the data folder.
