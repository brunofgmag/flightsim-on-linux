FSLabs A321 and Control Center

Tested with Control Center 2.0.1.197. The display patches below were flown on the test machine on 30 October 2026. The A321 needs nothing in the prefix beyond Proton FS2024, and one command checks everything it needs. It changes nothing, in the prefix or in the FSLabs folders.

Get it

The A321 and the Control Center come from flightsimlabs.com. The installer is an Inno Setup program called FSLControlCenter_2.0.1.197.exe. addon install fslabs-a321 prints this address and the kind of installer.

Install it

Run the FSLabs installer with the simulator and every other program of the prefix closed, one at a time, following the ground rules. On the test machine it went into the simulator's prefix on 14 October 2026, to C:\FlightSimLabs\ControlCenter, with FlightSimLabs2024\msfs_interface next to it. The program that ran it was not recorded, and no patch or setting was needed for the installer itself. Then activate the aircraft in the Control Center, as on Windows.

Make it run

The A321 needs Proton FS2024 for three reasons. Pick it for the simulator in Steam.

  • The cockpit displays are drawn with GDI+, and stock Wine skips four features of its gradient brushes. Each display then sits under a glare of white edges that fade to the centre, and the MCDU and clock letters lose their right side. With the brightness turned all the way down you can see the real picture underneath.
  • The EFB is a Chromium (CEF) page. Chromium checks that a page it locks was writable first. Stock Wine reports the wrong protection, so every renderer process stops at that check within half a second and the EFB stays dark. Proton FS2024 fixes this for cef_browser.exe, the process that hosts those renderers.
  • The displays also cost a lot of CPU in Wine's drawing code. On 29 October 2026, in flight, win32u.so held 24.6% of the simulator's cycles, spread over 44 threads. About 15 points were region arithmetic, 4.7 the blending of translucent images and 3.3 the enumeration of fonts. Seven Proton FS2024 patches came out of that and of the display faults, and the table lists them with the older gradient patch and one that targets a different stall.

addon apply fslabs-a321 changes nothing. It reports what exe.xml does with the Control Center and then runs the check.

The patches of 29 October together, in the flight of 30 October: win32u.so fell from 24.6% of the simulator's cycles to about 9% at 5,000 ft, and the simulator used 1 to 2 cores less there than on 29 October. The earlier measurement did not note the phase of flight, so that range is wide. A measurement on the ground does not compare, and the phase of flight moves the total more than the patches do.

The two SSE2 patches and the heap patch are written as expected because the first flight with them is still to be measured. Only a test program showed the SSE2 gains, and only the Proton build's own checks passed for the heap patch. In the flight of 30 October, at 5,000 ft, the blending and conversion functions still took about 1 core together, which is what the two SSE2 patches aim at.

Start it

From exe.xml

The Control Center writes its own entry in exe.xml, and the simulator starts it from there. On the test machine, under Wine's Wayland driver and on Proton FS2024, it opened that way, drew its window normally and validated the A321 licence. Nothing has to be set up for it.

By hand

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut fslabs-a321

This writes an entry called "FSLabs Control Center" in your application menu, with the program's own icon when 7z and magick are installed. With the simulator running, it starts the Control Center inside the simulator's container. Otherwise it starts it through the prefix. Either way it turns Direct3D 9 off for that one program: the Control Center opens without that, but it then takes 156 MiB of GPU memory, and the override keeps it off the GPU. It starts the program from its own folder, and with the Control Center already open it says so and does nothing. To start it from a terminal with the same options as exe.xml:

~/flightsim-on-linux/bin/flightsim-on-linux addon launch fslabs-a321 launch -- -NOTIFY

-NOTIFY is the option the Control Center's own exe.xml entry passes.

If you play inside gamescope

gamescope shows one window at a time. On the test machine the Control Center, started by the simulator, opened inside gamescope, covered the simulator and left it without a mouse pointer. Without gamescope, under the Wayland driver, it opened in its own window on the desktop, so skip this section unless you use gamescope.

Switch off the Control Center entry: in exe.xml, in the folder that holds UserCfg.opt, set its Disabled to True. Keep a copy of the file first. Then let a service start the Control Center with the aircraft:

~/flightsim-on-linux/bin/flightsim-on-linux addon apply simconnect-tcp
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher fslabs-a321

The first command makes the simulator listen for SimConnect clients on a TCP port above 1023, which is how the service learns which aircraft is loaded. The second writes a user service called flightsim-on-linux-fslabs-a321.service and switches it on. It looks at the simulator every 8 seconds. When the loaded aircraft's string contains "FSLabs A3" or "fsl-a32x" (case ignored; on the test machine the string was SimObjects\Airplanes\FSLabs A321-NEO PW\aircraft.CFG), it starts the Control Center with -NOTIFY inside the simulator's container, and never a second copy. It closes the Control Center only when the simulator closes, and only if the service started it. run gives the program the desktop's display, so it opens outside gamescope. A script of the test machine's own, older than this service, worked like this from 16 October 2026, and the Control Center validated the licence. This project's service has not yet been run with an FSLabs aircraft. exe.xml is still the plain way.

With that service file in place the check accepts the switched-off entry. Without it, a switched-off entry is a FAIL, because then nothing starts the Control Center.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check fslabs-a321

It prints one line for each of these, starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • the Proton's user_settings.py turns on copy-on-write tracking for cef_browser.exe;
  • the Proton's gdiplus.dll carries five patches: the gradient and centred text one and the ones for nested containers, source-copy text, font-family lookup and SSE2 premultiplying. fs2024-build.txt lists this repository's version of each, and the file is the one the build recorded;
  • the same for the three patches in win32u.so: larger font caches, banded regions and SSE2 blending;
  • the same for the heap patch in ntdll.dll;
  • exe.xml has the Control Center entry, switched on, or switched off with the service file above in place;
  • when that service file exists, SimConnect listens on a TCP port above 1023.

A line that lists patches names every one the build lacks. When one fails, rebuild Proton FS2024 with bin/flightsim-on-linux proton build. When the exe.xml line fails because the entry is missing, start the Control Center and run the check again. When it fails because the entry is switched off, the simulator won't start the Control Center, which is only right if the service above starts it.

Known problems

Changing aircraft freezes the simulator

On the test machine, switching from the A321 to another aircraft in the same session froze the simulator twice on 18 October 2026. To fly something else, quit the simulator and start it again. While the A321 is loaded, a thread inside the simulator keeps one CPU core at 100%, busy in Wine's locale and string-comparison functions called from the FSLabs module. The cause hasn't been found.

The automatic jetway call fails with GSX

When the A321 loads, it asks GSX for the jetway by itself. On the test machine that request failed in both sessions, because it arrived just as GSX was taking over the newly loaded aircraft, and the A321 doesn't reopen the GSX menu when it retries. Calling the jetway from the GSX menu worked in both. The same race could happen on Windows if GSX is slow to take over.

The Control Center log holds your key

AppData\Roaming\FlightSimLabs\CCLog.txt in the prefix stores the activation key in plain text. Never paste it into an issue, a forum post or an AI chat. For the same reason the launch script sends the Control Center's output to /dev/null and keeps no log of it.

Smaller textures for less VRAM

An A321neo uses about 4.2 GB of textures, and 46 of them are 8192 pixels wide. On the test machine, an RTX 4080 with 16 GB, the VRAM was full as soon as the cockpit loaded. A separate fix caps them:

~/flightsim-on-linux/bin/flightsim-on-linux addon apply fslabs-a321-textures

Every DDS file already carries its own smaller copies (mip levels), so the fix drops the largest levels and re-encodes nothing: what is left is, byte for byte, what the simulator shows from a little further away. Textures the exterior models use stop at 2048 pixels, and those of the cockpit at 4096, so the panels keep their sharpness. It also writes the new sizes into the package's layout.json. Across the whole package, 234 textures went from 5.4 GB to 0.9 GB, and one A321neo from about 4.2 GB to 2.7 GB. On 24 October 2026 the simulator stayed at about 13 GB with the A321neo at the gate, and the pilot saw no difference from the cockpit or the outside camera. Up close, the edges of the livery's lettering are slightly softer.

touches add-on files This changes the add-on's own files. The originals are kept in compatdata/2537590/flightsim-on-linux-backup/fslabs-a321-textures, and addon undo fslabs-a321-textures puts every one back. Run either with the simulator and the Control Center closed. To cap only the 8192-pixel textures, set FSL_TEXTURE_EXTERIOR=4096 before apply; FSL_TEXTURE_COCKPIT sets the cockpit cap. An FSLabs update brings the large textures back, and addon check fslabs-a321-textures then fails; run apply again.

Undo

addon undo fslabs-a321 has nothing to restore, because apply changes nothing in the prefix, and the Control Center entry in exe.xml is the Control Center's own. Take out the menu entry and the service with:

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut fslabs-a321 --remove
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher fslabs-a321 --off

Switch the exe.xml entry back on yourself if you turned it off for the service.
