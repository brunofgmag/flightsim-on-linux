FSLabs A321 and Control Center

Tested with Control Center 2.0.1.197 in October 2026. One command changes a single setting in the prefix, and another checks everything the A321 needs. Neither touches the FSLabs folders.

Before you start

The A321 needs Proton FS2024 for two reasons:

  • The cockpit displays are drawn with GDI+, and stock Wine skips four features of its gradient brushes. Each display then sits under a glare of white edges that fade to the centre, and the MCDU and clock letters lose their right side. With the brightness turned all the way down you can see the real picture underneath.
  • The EFB is a Chromium (CEF) page. Chromium checks that a page it locks was writable first. Stock Wine reports the wrong protection, so every renderer process stops at that check within half a second and the EFB stays dark. Proton FS2024 fixes this for cef_browser.exe, the process that hosts those renderers.

Pick Proton FS2024 for the simulator in Steam. Install the A321 and the Control Center with the FSLabs installer, and activate the aircraft in the Control Center, as on Windows. Run the installer with the simulator closed, following the ground rules.

Set up the prefix

~/flightsim-on-linux/bin/flightsim-on-linux addon apply fslabs-a321

Close the simulator first. The command makes WPF programs draw in software and then runs the check below.

The Control Center is a WPF program, and the simulator starts it from exe.xml, so it inherits the simulator's Direct3D 9, which is DXVK. On the test machine, WPF programs started that way under Wine's Wayland driver crashed the moment their window opened, with importing the supplied dmabufs failed. With this setting the Control Center opened from exe.xml and validated the A321 licence. The setting is the one in the ground rules, and it applies to every WPF program in the prefix. If it is already there, the command leaves it alone.

The command also reports what it finds in exe.xml, but it never edits that file. The Control Center writes its own entry there.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check fslabs-a321

It prints four lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • the Proton's user_settings.py turns on copy-on-write tracking for cef_browser.exe;
  • the Proton was built from this repository's GDI+ patch, and its gdiplus.dll is the one the build recorded;
  • WPF programs draw in software;
  • exe.xml has the Control Center entry, switched on.

When the first two fail, rebuild Proton FS2024 with bin/flightsim-on-linux proton build. When the last one fails because the entry is missing, start the Control Center and run the check again. When it fails because the entry is switched off, the simulator won't start the Control Center. That is only right if you start it yourself, as the gamescope section below explains.

Undo it

~/flightsim-on-linux/bin/flightsim-on-linux addon undo fslabs-a321

If the setup changed the WPF setting, undo puts back the value from before, or removes the setting if it wasn't there. Lorby AAO, AutoFPS, vRAAS and the Fenix runner rely on it too, and under the Wayland driver they crash without it.

Starting the Control Center yourself

With the simulator running, start it inside the simulator's container:

~/flightsim-on-linux/bin/flightsim-on-linux run 'C:\FlightSimLabs\ControlCenter\FSLControlCenter.exe' -NOTIFY

-NOTIFY is the option the Control Center's own exe.xml entry passes.

If you play inside gamescope

gamescope shows one window at a time. On the test machine the Control Center, started by the simulator, opened inside gamescope, covered the simulator and left it without a mouse pointer. Without gamescope, under the Wayland driver, it opened in its own window on the desktop, so skip this section unless you use gamescope.

Switch off the Control Center entry: in exe.xml, in the folder that holds UserCfg.opt, set its Disabled to True. Keep a copy of the file first. Then start the Control Center yourself, about 20 seconds after the simulator, with the command in the previous section. run gives it the desktop's display, so it opens outside gamescope. The test machine worked like this from 16 October 2026, with a small script that waited for the simulator, and the Control Center validated the licence. In this setup the check reports the switched-off entry as FAIL, and that is expected.

Changing aircraft freezes the simulator

On the test machine, switching from the A321 to another aircraft in the same session froze the simulator twice on 18 October 2026. To fly something else, quit the simulator and start it again. While the A321 is loaded, a thread inside the simulator keeps one CPU core at 100%, busy in Wine's locale and string-comparison functions called from the FSLabs module. The cause hasn't been found.

The automatic jetway call fails with GSX

When the A321 loads, it asks GSX for the jetway by itself. On the test machine that request failed in both sessions, because it arrived just as GSX was taking over the newly loaded aircraft, and the A321 doesn't reopen the GSX menu when it retries. Calling the jetway from the GSX menu worked in both. The same race could happen on Windows if GSX is slow to take over.

The Control Center log holds your key

AppData\Roaming\FlightSimLabs\CCLog.txt in the prefix stores the activation key in plain text. Never paste it into an issue, a forum post or an AI chat.
