Lorby Axis and Ohs

Tested with Axis and Ohs 4.58.2 on 24 October 2026, and in the add-ons prefix on 1 November 2026. It is a WPF program on wine-mono, and it needs a fix inside a copy of wine-mono, a Proton patch, and a launcher that opens it again when Mono deadlocks at startup.

Read this first

touches add-on files The fix changes wine-mono's files and leaves Axis and Ohs's own alone. apply makes a copy of Proton's wine-mono in your prefix, at drive_c/windows/mono/mono-2.0, and replaces WindowsBase.dll in that copy. Wine looks there before it looks in Proton's folder, so Proton's own files stay as they are, and every WPF program in the prefix that runs on wine-mono gets the change. Today that is Axis and Ohs alone: the Fenix runs on Microsoft's CLR, and vRAAS and the FSLabs Control Center are .NET 8. The copy is the same one GSX Pro uses, and the two add-ons share it. addon undo axis-and-ohs puts the original WindowsBase.dll back from the backup in compatdata/2537590/flightsim-on-linux-backup/axis-and-ohs, and deletes the copy when this tool made it and nothing else uses it.

Get it

Axis and Ohs is made by Lorby. Where to download it isn't recorded here. The file on the test machine was LorbyAxisAndOhs_Install_MSFS24.exe, version 4.58.2, installed to C:\Program Files\LorbyAxisAndOhs_MSFS24. Lorby's installation guide asks for .NET Framework 4.8 and the Visual C++ 2022 runtime. On the test machine the prefix had the C++ runtime and answered as .NET 4.8 through wine-mono, and the program opened.

Install it

Close the simulator and every other program in the prefix, and run nothing else while the installer works. The ground rules explain why. Then give the installer to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install axis-and-ohs ~/Downloads/LorbyAxisAndOhs_Install_MSFS24.exe

It refuses to start while the simulator runs or any program is open in the prefix, and names those programs. It runs the installer in the simulator's prefix with Proton's Wine. Which program ran the installer on the test machine wasn't recorded, and the installer itself needed nothing recorded either: no patch, no override.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply axis-and-ohs

Close the simulator first. It needs the .NET SDK, version 8 or newer (dotnet-sdk on Arch, dotnet-sdk-8.0 on Debian and Ubuntu), to build a small tool that restores Mono.Cecil 0.11.6 from NuGet while it builds. It does these things and runs the check:

  • The timer fix in WindowsBase.dll. Without it the script handler of Axis and Ohs dies about a minute after it loads the scripts of an aircraft, with Couldn't start scriptHandler TimeSpan period must be greater than or equal to zero. in LAAO_Startup_log.txt, and the Web API answers empty and zero to everything, which looks like "Axis and Ohs doesn't read the simulator". The cause: the autoscript timer adjusts its own interval. Every 100 ticks it compares the average of the last 10 measured periods with the interval it asked for. If they differ by 10 ms or less it lowers the interval by 5 ms, otherwise it raises it by 5. It starts at 75 ms. On Windows the timer fires on multiples of the system clock, 15.625 ms, so a 65 ms interval fires at 78 ms, the difference passes 10, and the interval goes up again; it settles around 65 to 70 ms. In Wine the timer fires at the time asked for, the difference never passes 10, and the interval goes down by 5 ms at a time to 0 and then tries -5, which the setter refuses. The arithmetic predicts the failure 61.5 s after the scripts start; it was measured at 62.1 s and 61.4 s on 15 October 2026. The fix makes DispatcherTimer.Interval round the value up to a multiple of 15.625 ms before the original checks, which stay as they were. That is the behaviour of the Windows clock, put in the setter. The tool writes the patched file next to the original and moves it into place in one step, because a running Axis and Ohs maps the original. After apply it reads the result back and refuses to keep it if it isn't patched. With the fix, Axis and Ohs ran 132 s and then 105 s with its scripts alive, (A:TITLE, String) returned the aircraft's title, and with the original file back it fell again at 61.4 s.
  • The Windows GAC off for mono. It sets * to gac=n under HKCU\Software\Wine\Mono\AsmOverrides. With .NET Framework 4.8 in the prefix, wine-mono looks in the Windows GAC first and loads Microsoft's WPF, and Axis and Ohs dies at start with MissingMethodException: BinaryCompatibility.get_TargetsAtLeast_Desktop_V4_5(). Before the 4.8 install that GAC had no assemblies, so the setting only brings back what mono did before. The .NET Framework 4.8 add-on sets the same value, so with it applied first this line only reports that the value is there. A gac=n that was already there is left alone and not removed by undo. Any other value of * is never replaced: apply says what it found, stops with an error and asks you to change it to gac=n yourself, then run apply again. undo deletes the value only while it is still the gac=n this tool wrote.
  • The add-ons prefix. Axis and Ohs runs in a second prefix with a Wine server of its own. apply makes it if it isn't there, writes its SimConnect.cfg, and sets * to gac=n in its registry too, which is a copy of the simulator's. Run addon apply simconnect-tcp first. The wine-mono copy lives in drive_c, which the two prefixes share.
  • Direct3D 9 off. That is not in the prefix: the launch script sets it for Axis and Ohs when it starts it.

It also needs Proton FS2024 with ntdll-heap-read-slack.patch. Axis and Ohs copies 7,200 bytes out of every SimConnect data message into a structure, and SimConnect.dll allocates each message with malloc at exactly the size of the message. On Windows the read past the block gets away with it. Under Wine a block could end a few bytes before memory that isn't mapped, and the copy crashed at a 64 KiB boundary. The patch keeps at least 64 KiB of readable memory after every heap block. A crash with this signature happened on 18 October 2026, and again on 22 and 24 October. Whether the patch stops them for good needs more flights; see "Known problems".

Start it

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut axis-and-ohs
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher addons-prefix axis-and-ohs

The first writes an entry called "Axis and Ohs" in your application menu, with the program's own icon when 7z and magick are installed. It starts Axis and Ohs in the add-ons prefix, with or without the simulator, with Direct3D 9 off for that one program. If it is already open, the entry says so and does nothing.

The second switches on two user services. addons-prefix keeps the prefix up, and flightsim-on-linux-axis-and-ohs.service starts the program. It looks every 8 seconds. About 20 seconds after a new simulator appears it waits, up to 5 minutes, for the GSX engine, couatl64_MSFS2024.exe, which the simulator starts from exe.xml, and then opens Axis and Ohs once for that simulator. It doesn't open a program you closed by hand until the next simulator. When the simulator it started Axis and Ohs for closes, it asks the program to end (SIGTERM, never a kill). A watcher is the way because exe.xml starts programs with the simulator's environment, which turns Direct3D 9 on, and nothing that exe.xml accepts can change that. Shortcuts and watchers has the rest.

The startup deadlock. Now and then Axis and Ohs opens and shows no window. Two threads compiling at once take two Mono locks in opposite order: one holds the loader lock and wants the lock of a generic-instance set, the other holds that one and wants the loader lock. Every 60 seconds the Wine log gets RtlpWaitForCriticalSection ... wait timed out in thread A, blocked by B, and the launcher answered "already open" at every click. It happened on 24 October 2026 at 18:58, and the openings at 14:10, 15:17, 15:40 and 19:02 that day were fine. Between the wine-mono of the prefix, 11.2.0, and versions 11.2.1 and 11.3.0 no commit mentions it, so a newer wine-mono doesn't cure it. So the launcher watches: for 180 seconds it reads the program's log every 5 seconds, and when the wait lines close a cycle between threads, it ends the program and opens it again, up to three tries, and then shows a notice. A long wait without a cycle doesn't count. Each try has its own log in FSOL_CACHE/logs/axis-and-ohs (aao-<date>.log, then -2 and -3); the last 20 are kept. The program's Wine log holds only Wine errors, which is what the detector reads. The launcher asks for those errors whether the simulator is open or not: the simulator's container passes the setting through, and the prefix launcher keeps what the caller sets. The retry hasn't run on a real deadlock yet. On 24 October 2026 the detector found the cycle in the log of the bad opening and nothing in the logs of the good ones, and a copy of the launcher with a stand-in program that printed those two lines closed it in 5 seconds and opened the second try; this repository's tests do the same with stand-ins.

The OpenDeck plugin

You need this only for the Axis and Ohs plugin of a Stream Deck in OpenDeck. Axis and Ohs answers with Access-Control-Allow-Origin: * twice. The webview of OpenDeck, a WebKitGTK page, joins the two into the invalid value *, * and hands every response to the plugin as an error. The plugin tests the connection with GET ?conn=1 every 500 ms; Axis and Ohs answers OK, the load event never fires, and the connection button stays dark with Axis and Ohs up. The plugin also asks with Cache-Control: no-cache, which forces an OPTIONS preflight, and Axis and Ohs answers that with 405. A small proxy fixes both:

~/flightsim-on-linux/bin/flightsim-on-linux addon launch axis-and-ohs cors-proxy

It listens on 127.0.0.1:43390, forwards to Axis and Ohs on 43380, sends each header once and answers the preflight with 204. While it runs, any web page open on this machine can call Axis and Ohs too, so stop it when you aren't using the plugin. It runs in the foreground; start it from a terminal or from a service of your own. In the plugin's settings.js change the port from 43380 to 43390; a plugin update brings 43380 back. Measured on 14 October 2026: with the proxy sending each header once the plugin's connected callback fired and the data loop began. A dark button with an empty title is a different problem: the Web API takes 150 ms per variable when Axis and Ohs has no data from the simulator, the plugin gives up at 500 ms, and reading (A:TITLE, String) from the API tells them apart, since an empty title means Axis and Ohs has no SimConnect.

Your profiles from Windows

If you copy your data from Windows, the folder is AppData\Local\LORBY_SI\LorbyAxisAndOhsMSFS24 in the prefix: the aircraft profiles in ConfigDatabase_MSFS2024.xml, the scripts in UserScripts_MSFS2024.xml, and the general settings. Two things in it stop matching.

  • Joystick GUIDs. A command is tied to the GUID of its joystick, and Wine gives a device another GUID than Windows did. The Wine GUID isn't in the prefix's registry, and it repeated in every start tested. Commands whose GUID doesn't match stay mute. Close Axis and Ohs, keep a copy of the database, and replace each Windows GUID with the one Axis and Ohs lists for the device in LAAO_Startup_log.txt. If Wine gives another GUID one day (another USB port, another Proton), the same replacement is needed again. Commands that use FlightLink, a virtual joystick that exists only on Windows, stay mute.
  • Aircraft paths. Profiles that recognise the aircraft by the path of its aircraft.cfg (airFileId) compare it with the path the AircraftLoaded event brings, with Contains in both directions and case-sensitive. Here the event brings the path in lower case under your packages folder. Cut the stored path down to the part from the top folder on (\community\..., \community2024\... or \streamedpackages\...), which the event's path contains wherever your library is.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check axis-and-ohs

It prints eight lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • three about the add-ons prefix, and two about its SimConnect.cfg;
  • the Proton build has ntdll-heap-read-slack.patch, and its ntdll.dll is the one the build recorded;
  • WindowsBase.dll in the wine-mono copy rounds timer intervals up, which it reads from the file without running anything;
  • * is gac=n under AsmOverrides in the add-ons prefix.

After a Proton update that brings another wine-mono, GSX Pro's apply copies the folder again, and the new copy starts without this patch: run addon apply axis-and-ohs again.

Known problems

  • The Mono deadlock at startup happens now and then. The launcher opens the program again, up to three times.
  • The first Web API query after a start returns empty.
  • Some strings fail with Illegal byte sequence.
  • The heap crash fix needs more flights. The crash came back on 22 and 24 October 2026 before the patch; since the patch there isn't enough flying to say it is gone.
  • Axis and Ohs needs the simulator's SimConnect. Without it the API answers 0 for every variable and the plugin's button stays dark.
  • On its own Wine server, Axis and Ohs doesn't see keyboard or mouse input while the simulator has the focus. That comes from reading Wine's code and wasn't measured. Joysticks and OpenDeck worked in the flight of 1 November 2026, started by the test machine's own scripts, and no command in the database uses a key. A keyboard shortcut you add would run into this.

Undo

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher axis-and-ohs --off
~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut axis-and-ohs --remove
~/flightsim-on-linux/bin/flightsim-on-linux addon undo axis-and-ohs

The first two take out the service and the menu entry. Close the simulator and Axis and Ohs first, then undo gives back the original WindowsBase.dll in the copy, removes the copy when this tool made it and GSX Pro doesn't use it, and deletes *=gac=n from the simulator's prefix if this tool added it. The add-ons prefix keeps its copy of that setting. Without the timer fix, Axis and Ohs falls back to dying about a minute after its scripts load.
