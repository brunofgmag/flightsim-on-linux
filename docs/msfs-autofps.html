MSFS AutoFPS

Tested with MSFS AutoFPS 0.5.5.0 on 1 November 2026. It takes a few steps rather than one command: the installer needs Direct3D 9 off and an empty prefix, and the program has to start inside the simulator's container, so it can't start from exe.xml.

Get it

The author publishes MSFS AutoFPS on the project's releases page on GitHub, where the downloads are public. Get MSFS_AutoFPS-installer-v0.5.4.4.exe or a newer one. It is a Windows installer with a WPF window.

Install it

Close the simulator and every program in its prefix first, and run nothing else while the installer works. The ground rules explain why. Then give the installer to the CLI:

~/flightsim-on-linux/bin/flightsim-on-linux addon install msfs-autofps ~/Downloads/MSFS_AutoFPS-installer-v0.5.5.0.exe

Without the file name it only prints where to get the program. With it, the command does three things the installer can't do for itself:

  • It refuses to start while the simulator runs or any program is open in the prefix, and names those programs.
  • It removes Community/autofps-html-widget-panel when that is a Linux link, and prints which link it removed and where it pointed. The installer replaces that folder by deleting it through Windows calls, and Wine can't delete a Linux link. On 16 October 2026 the 0.5.4.4 installer stopped at "Deleting old Widget Version" on a link made by a Community organiser. A real folder is never touched. If you want the link back, make it again after the install.
  • It runs the installer in the simulator's prefix with Direct3D 9 off for that one program, as the test machine installed it. The installer is a WPF program, and the reason is in "Make it run".

In the installer, leave "Close to Tray" checked if you want the tray icon. In AutoFPS's own settings, keep Auto-Start on "Retain". Choosing "MSFS" writes AutoFPS into exe.xml and renames that file to EXE.xml, and AutoFPS can't start from there anyway.

The in-app update has failed once and worked once. On 14 October 2026 AutoFPS offered 0.5.4.4, logged "Auto update in progress." and quit, and the installed version stayed 0.5.4.3. On 1 November 2026 it went from 0.5.4.4 to 0.5.5.0 by itself. If the version stays the same after an update, download the new installer and run the command above again.

Make it run

~/flightsim-on-linux/bin/flightsim-on-linux addon apply msfs-autofps

This changes nothing in the prefix, and then runs the check. AutoFPS needs three things, and none of them is a setting in the prefix:

  • Proton FS2024 with its tray icon patch. AutoFPS makes its tray icon in two calls. The second one names the icon by GUID only. Wine 11.0 looks an icon up by window and id and ignores the GUID, so the second call failed and AutoFPS 0.5.4.3 died at startup with TrySetMostRecentVersion failed. shell32-notifyicon-guid.patch makes Wine find the icon by GUID. On 16 October 2026, with the patch and "Close to Tray" checked, AutoFPS 0.5.4.4 created its tray icon and went on waiting for the simulator.
  • Direct3D 9 off for AutoFPS, set in the environment of the program when it starts. On 14 October 2026, on the Proton the test machine used then, AutoFPS died on its first frame inside the simulator's container with importing the supplied dmabufs failed. Four ways of turning Direct3D 9 off after the program started all failed, and only the environment of the process worked. Whether AutoFPS still needs it on Proton FS2024 was not measured, and the launch script keeps it off.
  • The simulator's container, because AutoFPS reads the simulator's memory. The launch script also empties DXVK_CONFIG for AutoFPS, so it sees the whole video memory of the card even when your launch options limit what the simulator sees.

Start it

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut msfs-autofps

This writes an entry called "MSFS AutoFPS" in your application menu, with AutoFPS's own icon when 7z and magick are installed, and a "Close MSFS AutoFPS" action. The entry starts AutoFPS inside the running simulator's container. With the simulator closed it tells you to start the simulator first, and with AutoFPS already open it says so and does nothing. The action asks AutoFPS's window to close, the way the close button does, and never kills the process. That matters: on 14 October 2026 a test run killed AutoFPS in flight, after it had lowered the simulator's terrain level of detail (TLOD) to its minimum and before it could put it back. Every start after that found the wrong TLOD in memory, failed its own compatibility check and cleared its saved memory addresses. If AutoFPS stays after the request, with "Close to Tray" on it goes to the tray instead of exiting, and you quit it from the tray menu. That is what the code expects. It has not been seen in flight.

To have it start by itself:

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher msfs-autofps

This writes a user service called flightsim-on-linux-msfs-autofps.service and switches it on. It looks for the simulator every 8 seconds. About 20 seconds after a new simulator appears, it starts AutoFPS, once for that simulator and never when AutoFPS is already open, so an AutoFPS you closed by hand stays closed until the next simulator. When the simulator closes and AutoFPS is still open, it asks AutoFPS to close and moves on. A service is the way because exe.xml starts its programs with the simulator's environment, which turns Direct3D 9 on. Nothing that exe.xml accepts, a path and a command line, can change that. Stopping the service leaves AutoFPS running, because a kill in flight can leave the TLOD lowered. Close it from its window before you end a flight early.

Check it

~/flightsim-on-linux/bin/flightsim-on-linux addon check msfs-autofps

It prints two lines, each starting with ok or FAIL, and changes nothing, so you can run it with the simulator open:

  • the Proton was built with shell32-notifyicon-guid.patch, and its shell32.dll is the one the build recorded;
  • Community/autofps-html-widget-panel is a real folder, not a Linux link and not missing.

When the first fails, rebuild Proton FS2024 with bin/flightsim-on-linux proton build. When the second fails, run the install command again.

Known problems

  • AutoFPS won't start from exe.xml, for the reason in "Start it".
  • "Elevated Privileges Detected" is expected under Wine. Nothing is wrong.
  • The in-app update doesn't install. Use the installer, as above.
  • VRAM+ does nothing without GPU-Z, because AutoFPS reads video memory from the shared memory that GPU-Z creates.
  • Killing AutoFPS in flight leaves the TLOD lowered. Close it from its window or the menu action.

Undo

Take out the menu entry and the service:

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut msfs-autofps --remove
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher msfs-autofps --off

addon undo msfs-autofps has nothing to restore, because apply changed nothing. If the install removed a Linux link from Community, the command printed where it pointed.
