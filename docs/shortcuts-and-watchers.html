Shortcuts and watchers

Two extras that some add-ons have. A menu entry starts the add-on's program the right way, from your application menu. A watcher is a background service that starts it for you when the simulator starts. Both live under your home folder, and one command takes each of them out again. Both passed their tests against a fake simulator, and the ones this project writes have not been through a real flight yet.

Every command below starts with ~/flightsim-on-linux/bin/flightsim-on-linux. The helper app has the same two things as Add menu shortcuts and Start add-ons with the simulator, and offers only the add-ons that have them.

What a menu entry is

An entry is two files, both outside the prefix and outside this project:

  • a .desktop file called flightsim-on-linux-<id>.desktop in ~/.local/share/applications (a second entry of the same add-on gets -2);
  • the icon, in ~/.local/share/icons/hicolor/256x256/apps.

If XDG_DATA_HOME is set, it replaces ~/.local/share. KDE and GNOME read the same folders. The test machine runs KDE, with its own earlier menu entries; the entries this project writes haven't been tried on a real desktop yet.

The entry runs flightsim-on-linux addon launch <id> <script>, with the full path of the command, so the add-on's own launch script decides how the program starts. When the program has to run inside the simulator's container, the script says start Microsoft Flight Simulator 2024 first; this program runs inside the simulator's container if the simulator is closed, and it is already running if you start it twice. With no terminal attached, those lines also arrive as a desktop notice, through notify-send, if you have it. An add-on with a close script adds a Close action to the entry's right-click menu.

Add and remove a menu entry

~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut <id>
~/flightsim-on-linux/bin/flightsim-on-linux addon shortcut <id> --remove

You can give several ids. The first command lists the files it wrote. If the add-on isn't installed yet, it says note <name> is not installed yet; the menu entry starts nothing until it is and writes the entry anyway. It then asks update-desktop-database and kbuildsycoca6 to reread the menu, if you have them.

--remove deletes only the files that carry this add-on's own marker, a line X-FlightsimOnLinux-Addon=<id>. An entry you made by hand stays. Because the entry holds the full path of the command, moving the project folder breaks it. Run addon shortcut <id> again from the new place.

Icons

The icon comes out of the program's own .exe. The command unpacks its icon resources with 7z, takes the largest one and shrinks it to at most 256 by 256 with ImageMagick's magick. So both programs have to be installed. Without them, or when the program is an AppImage, or when the .exe has no icon, the entry is written anyway with the default icon, and one line says why: no icon for <title>: <reason>; the menu entry has the default icon.

What a watcher is

A watcher is a user service called flightsim-on-linux-<id>.service, written to ~/.config/systemd/user (or XDG_CONFIG_HOME). It runs flightsim-on-linux addon watch <id>, one loop for every add-on. Every few seconds the loop looks at the running processes, 8 seconds apart unless the add-on says otherwise. The add-on's addon.json tells it which program to look for, which script starts it, when to start it and when to stop it. The service starts with your login session, which can be a couple of seconds before the desktop has set DISPLAY. So each time the loop starts a program, it reads DISPLAY, WAYLAND_DISPLAY and XAUTHORITY from systemctl --user show-environment and hands them to the script. Without them a Wine program can't create its window, and it closes.

One add-on has a watcher of another kind, the loop kind, for a job that is not starting a program. The service then runs one script of the add-on for as long as it lives, with flightsim-on-linux addon launch <id> <script>, and runs it again if it fails. It looks at nothing and starts nothing by itself. SayIntentions.AI uses it to keep its links out of Community while its Update Hub runs. Stopping a loop service stops the script. You switch it on and off with the same two commands as any other watcher, and the journal holds the script's own output instead of the loop's lines.

Why a watcher and not exe.xml

The simulator can start programs itself from exe.xml. A program started that way inherits the simulator's environment, and some programs only open with settings that environment overrides. MSFS AutoFPS is the example: the simulator's environment turns Direct3D 9 on, and on 14 October 2026, on the Proton the test machine used then, AutoFPS, a WPF program, died on its first frame with importing the supplied dmabufs failed. Nothing that exe.xml accepts, a path and a command line, can turn it off again. Whether Proton FS2024 still needs it was not measured. A watcher starts the program from its own launch script, where the environment is under the add-on's control.

The rule used here is that WPF programs start from a watcher and the rest from exe.xml. It is decided by what the program imports. The Fenix bootstrapper is one exception, because it refuses to run any other way than from exe.xml. The FSLabs Control Center is another: its guide has both ways.

When it starts and what stops

By default the watcher starts the program once for each simulator process, about 20 seconds after the simulator appears, and never when the program is already running. A program you close by hand stays closed until the next simulator. Some add-ons wait for another process first, or start only when the simulator loads a matching aircraft.

Three add-ons keep their program up instead, and look at the state every 8 seconds. addons-prefix keeps its program running whether or not the simulator is there. sentinel keeps it running while the simulator is. active-sky keeps ActiveSky Utils running while the sentinel is. A program of theirs that dies comes back at the next look.

What happens when the simulator closes depends on the add-on's stop setting. With never, the watcher leaves the program alone. With with_simulator, it stops the program when the simulator closes. with_simulator_if_started does the same, but leaves a program you opened yourself. on_other_aircraft stops the program when a different aircraft loads, and when the simulator closes if the watcher started it.

To stop a program, the watcher runs the add-on's close script if it has one. Otherwise it sends the program SIGTERM. It never sends SIGKILL, because killing some programs in flight leaves the simulator changed: AutoFPS killed in flight leaves the terrain level of detail lowered. The service itself uses KillMode=process, so stopping or switching off the service leaves the program running, whatever stop says.

Switch a watcher on and off

~/flightsim-on-linux/bin/flightsim-on-linux addon watcher <id>
~/flightsim-on-linux/bin/flightsim-on-linux addon watcher <id> --off

The first command writes the service file and runs systemctl --user enable --now on it, then says wrote <path> and switched it on. The second disables the service and deletes the file, and says that <unit> is off and its file is deleted. If systemctl fails, the line says FAIL and gives its exit code. Both need a systemd user session.

Reading a watcher's log

The service writes to the journal. To read it, or to follow it as it grows:

journalctl --user -u flightsim-on-linux-<id>
journalctl --user -u flightsim-on-linux-<id> -f

The loop writes one line for each change of state, never one for each look, and each line starts with the time. The lines you can expect are watching for <name>, simulator <pid> running, starting the program, the program is already running; leaving it alone, simulator <pid> closed and closing the program the simulator no longer needs. A script that fails shows as <script> exited with code <n>. systemctl --user status flightsim-on-linux-<id> says whether the service itself is running.

The aircraft trigger

A few programs should start only for one aircraft. The FSLabs Control Center, for example, starts when an FSLabs aircraft loads. For that the watcher has to ask the simulator which aircraft loaded, and it asks over SimConnect. That needs three things:

  • Node.js, with node on your path;
  • the node-simconnect module, which the base add-on simconnect-tcp installs when you run flightsim-on-linux addon apply simconnect-tcp and npm is installed;
  • a simulator that listens for SimConnect on TCP. By default its SimConnect.xml declares port 500, and Linux doesn't let the simulator open ports below 1024. The same simconnect-tcp add-on moves it to 5111 and its check fails below 1024.

If Node.js is missing, the log says node is not installed; the aircraft trigger needs Node.js. If the module is missing, it says node-simconnect is missing; run: flightsim-on-linux addon apply simconnect-tcp; trying again every 60 s. Either way the watcher says it once and tries again every minute, and nothing else about it changes. The trigger has run against a fake simulator only.

Nothing restarts without a limit

  • The program starts once for each simulator process. With an aircraft trigger it starts on each matching aircraft when it isn't already running. The three add-ons that keep a program up are the exception: they start it again at every look, 8 seconds apart, for as long as it keeps dying.
  • A health restart, for an add-on that restarts its program when the simulator is up and the program has had no connection to it for a set time, runs at most three times for each simulator process, that set time apart. After the third the log says restarted 3 times without a connection; giving up until the simulator restarts.
  • The helper process that reads the aircraft is started again 8 seconds after it dies.
  • A script that is still running after 120 seconds is killed, the log says so, and the loop moves on. A program the script already started keeps running.
  • The service uses Restart=on-failure with a pause of 5 seconds.
